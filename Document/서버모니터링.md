# 서버 상태 모니터링 구현 및 운영 기준

> 최종 갱신: 2026-07-26
>
> 이 문서는 현재 구현을 기준으로 작성한다. 명시적으로 `후속 후보`라고 표시한 항목은 아직 노출되지 않는다.

## 1. 목적

GameServer, GatewayServer, LoginServer, RegistryServer, CommunicationServer와 공통 라이브러리의 상태를 운영 중에 파악한다.

다음 질문에 대시보드와 알림으로 답할 수 있어야 한다.

- 서버가 정상적으로 실행 중이고 요청을 처리하고 있는가?
- 네트워크, DB, ContentsThread 중 어디에서 지연과 backlog가 발생하는가?
- GameServer별 유저와 Stage 수가 어떻게 분포하는가?
- GameServer 전체에서 몬스터, 스킬 효과, 투사체 등 어떤 객체가 증가하고 있는가?
- Gateway의 인증, 라우팅, fan-out과 GameServer 연결이 정상인가?
- 패킷 풀, queue, container 또는 OS 자원이 지속적으로 증가하고 있는가?
- 서버 장애가 발생하기 전에 경고할 수 있는가?

개별 Stage, ContentsThread, PacketPool capacity별 상세 series는 만들지 않는다. 운영 metric은 서버 단위 합계와 제한된 고정 label만 사용하고, 개별 객체 분석은 요청 시 진단으로 분리한다.

## 2. 범위와 전제

- 서버는 Windows, C++ 20 기반이다.
- 서버 tick 기본 주기는 50ms다.
- Stage는 하나의 ContentsThread에 소유되며 Stage 상태는 해당 스레드에서만 접근한다.
- 초기 AWS 배포는 EC2를 기준으로 하지만 애플리케이션 계측은 AWS에 종속시키지 않는다.
- 운영 메트릭 저장과 조회는 Prometheus 형식을 기준으로 한다.
- 유저 ID, 캐릭터 ID, Stage runtime ID처럼 계속 증가하는 값은 일반 메트릭 label로 사용하지 않는다.
- 개인정보, 인증 토큰, 채팅 본문, IP 주소, SQL 문자열은 메트릭에 기록하지 않는다.

## 3. 전체 구성

### 3.1 기본 도구

| 영역 | 도구 | 역할 |
|---|---|---|
| 애플리케이션 메트릭 | Prometheus 형식의 `/metrics` | 서버별 Counter, Gauge, Histogram 노출 |
| 메트릭 수집·저장 | Prometheus 또는 Amazon Managed Service for Prometheus | 주기적 scrape와 시계열 저장 |
| 대시보드·경보 상태 | Grafana + Prometheus alert rule | 조회, 대시보드, 경보 판정. 외부 전송은 현재 사용하지 않음 |
| Windows process·호스트 | 서버 내 Windows API publisher | process CPU/memory/handle/I/O와 Registry의 host CPU/memory |
| 로그 | 기존 Logger + CloudWatch Agent | 로그 파일 중앙 수집과 검색 |
| 분산 추적 | OpenTelemetry + Collector | 초기 필수 범위가 아니며 병목 분석 단계에서 선택 도입 |

### 3.2 데이터 흐름

1. 각 서버 프로세스는 내부 전용 monitoring port에 `/metrics`를 제공한다.
2. Prometheus 또는 Collector가 기본 15초 주기로 각 서버 endpoint를 scrape한다.
3. Grafana가 저장된 메트릭을 조회하고 Prometheus가 경보 상태를 판정한다. 외부 알림 전달 도구는 현재 구성하지 않는다.
4. 로그는 애플리케이션 hot path에서 외부로 직접 보내지 않고 현재 비동기 파일 로깅 후 Agent가 수집한다.

모니터링 port는 인터넷에 공개하지 않는다. 로컬 Prometheus 또는 지정된 VPC 보안 그룹에서만 접근을 허용한다.

### 3.3 공통 기반 구현 현황

ServerBase에 공통 계측 기반이 구현되어 있다. Prometheus C++ client library는 사용하지 않으며 HTTP endpoint만 header-only `cpp-httplib`를 사용한다.

- `MetricsRegistry`: 고정 label 기반 Counter, Gauge, Histogram 등록과 Prometheus text format 출력. 공용 metric은 값 타입별 `GaugeMetric`, `CounterMetric`, `HistogramMetric` enum으로 등록·갱신한다.
- `MetricsHttpServer`: `cpp-httplib v0.50.1`의 게임 IOCP와 분리된 listener thread 및 단일 worker에서 `GET /metrics`, `GET /health` 처리
- `WindowsMetricsPublisher`: 모든 서버의 process metric과 RegistryServer의 host metric을 Windows API로 게시
- hot path: 모든 metric은 값 타입별 enum으로 Registry의 고정 series 배열을 조회한 뒤 relaxed atomic만 갱신한다. subsystem은 개별 metric pointer를 보관하지 않는다.
- scrape path: Net/DB/Windows/Contents/Game snapshot을 Registry에 게시한 뒤 immutable metric 목록을 Prometheus text format으로 직렬화
- 종료: ServerBase shutdown에서 endpoint thread를 먼저 깨우고 join

현재 모든 서버가 다음 공통 metric을 노출한다.

- `mmo_server_info{server_type,server_id}`. 이 label은 application이 넣고, Prometheus target에도 같은 식별 label을 설정한다.
- `mmo_server_ready`
- `mmo_server_shutting_down`
- `mmo_server_uptime_seconds`
- `mmo_metrics_scrapes_total`
- `mmo_metrics_scrape_errors_total`
- `mmo_metrics_scrape_duration_seconds`
- `mmo_metrics_response_bytes`

NetLib/Session/PacketPool 계측도 구현되어 있다.

- 완료된 IO 기준 send/recv byte와 packet, posted/completed/error counter
- 실제 연결 상태 기준 active session, 전체 recv buffer/send queue/in-flight gauge
- PacketPool 전체 alloc/free/new/scan miss와 held/in-use/hit ratio, 버킷 중 최대 shard imbalance
- PacketPool의 shard lock 스냅샷은 첫 scrape 후 30초마다만 갱신

ContentsThread와 AsyncDBQueue 계측도 구현되어 있다.

- 전체 ContentsThread의 소유 Contents, pending add/remove, task queue와 처리·예외 합계
- tick 실행시간, 예정 시각 대비 지연, update interval 초과 횟수
- DB 종류와 query/transaction별 queue wait, 실행시간, queue/active 수와 결과
- 모니터링 비활성 시 DB 요청당 추가 시간 측정을 수행하지 않음

`MetricsRegistry`는 하나의 enum 값당 하나의 고정 series만 보관한다. 과거의 `MetricScopeId`와 scope별 동적 series 저장 구조는 제거되었다. 같은 family 안의 고정 label 조합이 여러 개 필요하면 조합마다 별도의 의미 있는 enum 값을 선언한다.

설정은 각 서버 ini의 `[Monitoring]`을 사용한다.

```ini
[Monitoring]
Enabled = true
IP = 127.0.0.1
Port = 19201
```

- 로컬 수집기는 `127.0.0.1`을 사용한다.
- 다른 host의 수집기가 접근할 때만 서버의 VPC private IP로 바꾸고 지정된 수집기 보안 그룹만 port 접근을 허용한다.
- `0.0.0.0`, 도메인명, 0 또는 범위 밖 port는 기동 시 거부한다.
- 같은 host에서 실행하는 각 서버는 서로 다른 port를 사용한다.

기본 로컬 port는 Registry 19001, Login 19010, Communication 19020, Gateway 19100, Game 19201이다.

### 3.4 현재 Prometheus와 Grafana 연결

- `Development/Monitoring/prometheus/prometheus.yml`은 `static_configs`로 위 5개 `127.0.0.1:port` target을 선언한다.
- 별도 설정이 없으므로 Prometheus는 각 target의 `http://IP:port/metrics`를 15초마다 요청한다.
- 서버 INI의 `IP`와 `Port`는 HTTP endpoint의 bind 주소이고, Prometheus의 `targets`는 접속 주소다. 두 설정은 자동 동기화되지 않는다.
- Grafana datasource provisioning은 `http://127.0.0.1:9090`의 Prometheus를 `uid=prometheus`, proxy 방식으로 등록한다.
- 브라우저는 게임 서버나 Prometheus에 직접 질의하지 않는다. Grafana server가 dashboard의 PromQL을 Prometheus HTTP API에 보내고 결과를 시각화한다.

현재 file-based service discovery는 사용하지 않는다. 서버 인스턴스가 많아지면 배포 시스템이나 별도 Registry 연동 도구가 완성된 target JSON을 임시 파일에 작성한 뒤 원자적으로 교체하고, Prometheus `file_sd_configs`가 그 경로를 감시하는 방식으로 전환한다. Prometheus가 JSON을 자동 생성하거나 metric port를 추론하지는 않는다.

## 4. 수집 단계

모든 상태를 같은 방식과 주기로 수집하지 않는다.

### 4.1 상시 운영 메트릭

- Counter, 현재 개수, queue depth, 처리 시간처럼 장애 탐지에 필요한 값이다.
- 이벤트 발생 시 고정 배열 또는 `memory_order_relaxed` atomic을 갱신한다.
- scrape 기본 주기는 15초다.
- 문자열 생성, 동적 할당, 동적 label 탐색을 hot path에서 수행하지 않는다.

### 4.2 저빈도 합계 스냅샷

- Stage container 합계, PacketPool shard 분포처럼 수집 자체에 lock 또는 순회가 필요한 값이다.
- 상태 소유 스레드가 기본 5초 주기로 생성한다.
- PacketPool처럼 여러 lock이 필요한 통계는 기본 30초 주기로 제한한다.
- exporter는 원본 객체가 아니라 마지막으로 발행된 스냅샷만 읽는다.

### 4.3 요청 시 진단

- 개별 Stage runtime ID, sector 전체 분포, 모든 packet ID, 특정 유저 흐름처럼 cardinality나 비용이 큰 정보다.
- Prometheus 상시 메트릭으로 만들지 않는다.
- 관리자 명령 또는 별도 진단 dump로 한 번만 생성하고 로그나 파일로 남긴다.

## 5. 메트릭 공통 규약

### 5.1 타입

- `Counter`: 누적 이벤트 수 또는 누적 byte. 이름은 `_total`로 끝낸다.
- `Gauge`: 현재 값. 증가와 감소가 모두 가능하다.
- `Histogram`: latency, tick duration, fan-out 크기 같은 분포다.
- 프로세스 내부에서 percentile을 계산하지 않고 Prometheus에서 p50, p95, p99를 계산한다.

### 5.2 이름과 단위

- 프로젝트 prefix는 `mmo_`를 사용한다.
- 시간은 초 단위이며 이름은 `_seconds`로 끝낸다.
- 크기는 byte 단위이며 이름은 `_bytes`로 끝낸다.
- 비율은 0~1이며 이름은 `_ratio`로 끝낸다.
- 동일 개념은 metric 이름을 동적으로 만들지 않고 제한된 label로 구분한다.

현재 `mmo_stage_objects_total`은 누적 Counter가 아니라 `object_type="all"`을 포함한 현재 object 개수 Gauge다. 여기서 `_total`은 시간 누적이 아니라 전체 object view라는 기존 의미이므로 PromQL에서 `rate()`를 적용하지 않는다.

### 5.3 공통 label

application metric에 다음 resource 정보를 매번 중복 label로 넣지 않는다. 현재 static target에는 `server_type`, `server_id`를 설정하고 Prometheus가 `job`, `instance`를 자동 추가한다.

- `server_type`: `game`, `gateway`, `login`, `registry`, `communication`
- `server_id`: 설정에 있는 서버 ID
- `instance`: Prometheus target instance

현재 `environment=local`은 Prometheus `external_labels`로만 설정한다. 운영의 `environment`와 `build_version`은 remote write/federation 또는 배포 시스템 연동이 필요해질 때 target/resource label로 추가한다.

### 5.4 label 제한

허용되는 label 값은 코드 또는 설정으로 범위가 제한되어야 한다.

허용 예:

- `operation=query|transaction`
- `result=success|business_failure|db_error`
- `reason=known|unknown|graceful|abnormal`
- `object_type=all|character|monster|prop|drop`

금지 예:

- accountId, characterId, objectId, projectileId
- 인증 토큰, IP 주소, 채팅 메시지
- 원본 SQL과 예외 메시지 전체
- 무제한으로 생성되는 runtime stageId

Stage 식별자, data key, channel은 상시 label로 노출하지 않는다. Stage 상태는 서버별 합계와 최대값으로 게시하고 개별 Stage 정보는 요청 시 진단으로만 확인한다.

## 6. 공통 서버 메트릭

모든 서버가 상속하는 ServerBase에서 현재 다음 값을 제공한다.

| Metric | 타입 | 의미 |
|---|---|---|
| `mmo_server_info{server_type,server_id}` | Gauge | 값은 항상 1, application의 서버 종류와 ID 제공 |
| `mmo_server_uptime_seconds` | Gauge | 프로세스 가동 시간 |
| `mmo_server_ready` | Gauge | 초기화와 필수 연결 완료 여부 |
| `mmo_server_shutting_down` | Gauge | graceful shutdown 진행 여부 |
| `mmo_metrics_scrapes_total` | Counter | 성공한 `/metrics` 응답 누계 |
| `mmo_metrics_scrape_errors_total` | Counter | 수집 또는 직렬화 실패 누계 |
| `mmo_metrics_scrape_duration_seconds` | Histogram | `/metrics` 생성 시간 |
| `mmo_metrics_response_bytes` | Gauge | 직전 `/metrics` 응답 크기 |

`/health`는 HTTP endpoint 생존만 확인한다. 실제 서비스 준비 여부는 `mmo_server_ready`로 판단한다. scrape self metric은 응답 본문 생성 후 갱신되므로 현재 요청의 결과는 다음 scrape부터 보인다.

## 7. Windows와 프로세스 메트릭

별도 windows_exporter를 사용하지 않고 서버가 저비용 Windows API를 scrape 시점에 호출한다.

| Metric | 게시 대상 | 의미 |
|---|---|---|
| `mmo_process_cpu_seconds` | 모든 서버 | process kernel+user CPU 누적 시간 |
| `mmo_process_working_set_bytes` | 모든 서버 | 현재 working set |
| `mmo_process_peak_working_set_bytes` | 모든 서버 | process lifetime peak working set |
| `mmo_process_private_bytes` | 모든 서버 | private committed memory |
| `mmo_process_handle_count` | 모든 서버 | 열린 Windows handle 수 |
| `mmo_process_io_read_bytes_total` | 모든 서버 | process read byte 누계 |
| `mmo_process_io_write_bytes_total` | 모든 서버 | process write byte 누계 |
| `mmo_process_io_other_bytes_total` | 모든 서버 | read/write 외 I/O byte 누계 |
| `mmo_host_cpu_seconds{mode}` | RegistryServer | `idle`, `system`, `user` host CPU 누적 시간 |
| `mmo_host_memory_total_bytes` | RegistryServer | 전체 physical memory |
| `mmo_host_memory_available_bytes` | RegistryServer | 사용 가능한 physical memory |
| `mmo_windows_metrics_collection_errors_total{scope}` | 모든 서버/Registry | `process`, `host` 수집 실패 누계 |

동일 host 값을 서버 수만큼 중복 저장하지 않도록 host metric은 RegistryServer만 게시한다. RegistryServer가 종료되면 host metric도 중단되며 `MmoServerDown`으로 함께 탐지한다. disk, NIC, TCP, service 상세 상태는 현재 native publisher 범위에 포함하지 않는다. application network 상태는 NetLib metric으로 계속 수집한다.

## 8. NetLib와 Session 메트릭

### 8.1 연결과 오류

| Metric | 타입 | 현재 label/의미 |
|---|---|---|
| `mmo_net_accept_total` | Counter | accept 성공 누계, label 없음 |
| `mmo_net_sessions_created_total` | Counter | Session 객체 생성 누계 |
| `mmo_net_sessions_destroyed_total` | Counter | Session 객체 소멸 누계 |
| `mmo_net_sessions_active` | Gauge | 현재 연결된 전체 Session 수 |
| `mmo_net_disconnect_total{reason}` | Counter | `graceful`, `abnormal` |
| `mmo_net_invalid_packet_total{reason="header"}` | Counter | 거부된 잘못된 packet header |
| `mmo_net_recv_errors_total{reason}` | Counter | `known`, `unknown` recv 오류 |
| `mmo_net_send_errors_total{reason}` | Counter | `known`, `unknown` send 오류 |
| `mmo_net_connect_posted_total` | Counter | 게시한 ConnectEx 수 |
| `mmo_net_connect_completed_total` | Counter | 완료된 ConnectEx 수 |
| `mmo_net_connect_failed_total` | Counter | 실패한 ConnectEx 수 |

OS error code 원문을 label로 사용하지 않는다. 알려진 작은 reason class로 매핑하고 원본 error code는 rate limited 로그에 남긴다.

### 8.2 송수신과 backlog

| Metric | 타입 | 의미 |
|---|---|---|
| `mmo_net_recv_bytes_total` | Counter | IOCP recv 완료 byte |
| `mmo_net_send_bytes_total` | Counter | IOCP send 완료 byte |
| `mmo_net_recv_packets_total` | Counter | header 검증 후 ring buffer에서 완전히 조립된 packet 수 |
| `mmo_net_send_packets_total` | Counter | send completion에서 해제된 application packet 수 |
| `mmo_net_recv_posted_total` | Counter | 게시한 WSARecv 수 |
| `mmo_net_recv_completed_total` | Counter | recv completion 수 |
| `mmo_net_send_posted_total` | Counter | 게시한 WSASend 수 |
| `mmo_net_send_completed_total` | Counter | send completion 수 |
| `mmo_net_recv_buffer_used_bytes` | Gauge | 전체 Session의 현재 사용량 합계 |
| `mmo_net_send_queue_packets` | Gauge | 전체 대기 packet 수 |
| `mmo_net_send_queue_bytes` | Gauge | 전체 대기 byte |
| `mmo_net_send_inflight_packets` | Gauge | WSASend가 참조 중인 packet 수 |
| `mmo_net_send_inflight_bytes` | Gauge | WSASend가 참조 중인 byte |
| `mmo_net_recv_buffer_full_total` | Counter | recv buffer full disconnect 수 |

Session별 label은 만들지 않는다. Session 내부 값은 global 또는 listener/peer type 단위로 합산한다.

### 8.3 packet ID별 상세 — 미구현 후속 후보

현재 packet ID별 count와 byte는 노출하지 않는다. 추가한다면 고정 크기 배열로 수집하고 hot path에서 metric 객체나 문자열을 조회하지 않는다.

- 운영 endpoint에는 사전에 정한 핵심 packet ID만 노출한다.
- 전체 packet ID는 요청 시 dump하거나 저빈도 상위 N개만 계산한다.
- packet ID 값은 제한된 enum이지만 전체 노출 여부는 실제 시계열 수 예산을 확인한 뒤 결정한다.

## 11. AsyncDBQueue 메트릭

현재 모든 DB가 하나의 FIFO와 worker pool을 공유하므로 queue 지연과 head-of-line blocking을 함께 관찰한다.

| Metric | 타입 | 권장 label |
|---|---|---|
| `mmo_db_queue_depth` | Gauge | `db_type`, `operation` |
| `mmo_db_queue_oldest_age_seconds` | Gauge | 없음 |
| `mmo_db_active_requests` | Gauge | `db_type`, `operation` |
| `mmo_db_requests_total` | Counter | `db_type`, `operation` |
| `mmo_db_results_total` | Counter | `db_type`, `operation`, `result` |
| `mmo_db_rejected_total` | Counter | `db_type`, `operation` |
| `mmo_db_queue_wait_seconds` | Histogram | `db_type`, `operation` |
| `mmo_db_execution_seconds` | Histogram | `db_type`, `operation` |

현재 `operation`은 `query|transaction`, `db_type`은 `account|game`, `result`는 `success|business_failure|db_error`로 고정한다. SQL 문자열, table 이름의 동적 조합, accountId, dbIndex, shard host를 label로 사용하지 않는다. 로그인·캐릭터 로드 같은 도메인 operation 구분은 실제 필요성과 시계열 예산을 확인한 뒤 API에 제한된 enum을 추가한다.

DB queue는 하나의 전역 FIFO지만 각 요청이 가진 고정 분류별 depth도 함께 증감한다. 전체 depth는 `sum(mmo_db_queue_depth)`로 계산한다. `mmo_db_queue_oldest_age_seconds`는 scrape 시 queue mutex를 짧게 획득해 front의 enqueue 시각만 읽으며 요청이나 SQL을 순회하지 않는다.

transaction retry 횟수, reconnect 결과, connection idle/used, coroutine resume delay는 아직 노출하지 않는다. 현재 단계는 queue 병목과 DB 실행 지연을 분리하는 최소 운영 계측을 우선한다.

## 13. Stage 스냅샷

### 13.1 스레드 소유권

Stage container는 Stage의 ContentsThread만 읽고 변경한다. exporter 또는 별도 monitoring thread가 `m_users`, `m_objects` 등을 직접 조회하지 않는다.

Stage는 기본 5초마다 자기 스레드에서 상태를 작은 snapshot으로 복사한다. scrape 시 StageManager가 snapshot들을 합산해 서버 전체 gauge를 갱신하므로 exporter가 Stage container를 직접 읽지 않는다.

대부분은 기존 container의 `size()`를 사용한다. buff/cast/monster skill, 실제 player projectile 수와 sector 점유/max처럼 합계 계산이 필요한 값만 5초 주기로 관련 container를 순회한다. 이 순회 비용은 Stage 부하 테스트에서 측정하고, 과도하면 active counter 또는 더 긴 진단 주기로 전환한다.

### 13.2 Stage 합계 상태

모든 값은 GameServer 전체 합계이며 Stage 식별 label을 갖지 않는다. `object_type`, `owner_type`, `actor_type`처럼 값 범위가 고정된 분류 label만 유지한다.

| Metric | 타입 | 의미 |
|---|---|---|
| `mmo_game_stage_user_hint_total` | Gauge | 모든 Stage의 유저 수 hint 합계 |
| `mmo_stage_objects_total{object_type}` | Gauge | 통합 object 수와 character, monster, prop, drop 분류별 합계 |
| `mmo_stage_area_effects` | Gauge | 활성 AreaEffect 합계 |
| `mmo_stage_projectile_groups` | Gauge | 플레이어 ProjectileGroup 합계 |

| `mmo_stage_active_casts{actor_type}` | Gauge | 현재 cast 중인 actor 합계 |
| `mmo_stage_active_buffs{actor_type}` | Gauge | 활성 buff instance 합계 |

### 13.4 container 메모리 진단

다음 정보는 아직 상시 metric으로 구현하지 않은 요청 시 진단 후보다.

- vector: `size`, `capacity`
- unordered_map: `size`, `bucket_count`, `load_factor`
- queue: depth, oldest item age, high watermark
- scratch buffer: capacity와 최근 사용 최대값

추가할 경우 Stage label 조합을 늘리지 않고 diagnostic snapshot 또는 전체 Stage의 max/합계로 제공한다. 실제 메모리는 container 크기만으로 정확히 계산할 수 없으므로 process private bytes와 함께 판단한다.

## 16. 로그와 추적

메트릭은 상태와 추세를 찾고 로그는 개별 실패 원인을 찾는다.

- 모든 Error/Warn 로그에 `serverType`, `serverId`, component, event 이름을 구조적으로 포함한다.
- accountId가 진단에 필요하면 메트릭 label이 아니라 접근이 제한된 로그에 기록한다.
- 반복 오류는 rate limit 또는 집계 로그를 적용해 장애 시 로그 폭주를 막는다.
- metric alert에서 관련 로그를 찾을 수 있도록 operation과 reason class의 명칭을 통일한다.

OpenTelemetry trace는 초기 구현 범위에서 제외한다. 다음 흐름에서 원인 분리가 어렵다고 확인될 때 제한적으로 추가한다.

- Login → Gateway 인증
- Gateway → GameServer 최초 입장
- cross-server Stage 이동
- DB load/save와 coroutine resume

모든 game tick, 모든 AOI packet, 모든 monster update를 trace span으로 만들지 않는다.

## 19. 구현 시 동시성 규약

### 19.1 Counter

- IOCP와 여러 thread가 동시에 갱신하는 Counter는 `std::atomic<uint64>`와 `memory_order_relaxed`를 사용한다.
- contention이 확인된 hot counter는 cache line 정렬한 per-thread atomic counter로 분산하고 scrape 시 합산한다.
- 일반 `uint64` per-thread 값을 다른 스레드가 동시에 읽지 않는다.

### 19.2 Gauge와 snapshot

- 단순 global 개수는 atomic gauge를 생성·삭제 진입점에서 증감한다.
- Stage 상태는 Stage 소유 스레드가 5초마다 snapshot을 작성하고 mutex 아래 교체한다.
- StageManager는 scrape 시 각 Stage의 작은 snapshot을 mutex 아래 복사한 뒤 서버 합계와 최댓값을 계산한다.
- ContentsThread의 현재 상태는 relaxed atomic snapshot으로 게시하며 ServerBase가 scrape 직전에 합계와 oldest-age 최댓값을 계산한다.
- exporter는 Stage나 ContentsThread의 원본 container를 직접 읽지 않는다.

### 19.3 Histogram

- bucket 경계는 초기화 때 고정한다.
- 관측 시 동적 allocation과 문자열 label lookup을 하지 않는다.
- 시간 측정이 매우 빈번한 경로에 sampling을 추가할 경우 적용 위치와 비율을 문서화한다. 현재 ContentsThread와 DB latency histogram은 sampling하지 않는다.

### 19.4 기존 코드의 선행 수정 사항

1. `NetLibStats`의 TLS 배열을 per-thread relaxed atomic으로 변경해 snapshot thread의 동시 읽기를 안전하게 만든다. **완료.**
2. `Stage::GetUserCountHint()`가 map을 직접 읽지 않고 Stage thread가 갱신하는 atomic count hint를 읽게 한다. **완료.**
3. `PacketPool::GetStats()`는 모든 shard lock을 획득하므로 첫 scrape 후 30초 주기의 snapshot에서만 호출한다. **완료.**

1~2번은 모니터링 기능 추가 전에 별도 단계로 구현했고, 3번은 NetLib 계측 단계에서 적용했다.

## 20. 성능 예산과 검증

### 20.1 목표

Release 부하 테스트에서 모니터링 활성화 전과 비교한다.

- process CPU 증가: 평균 1% 이내를 목표
- ContentsThread tick p99 증가: 1ms 이내를 목표
- peak memory 증가: metric series와 snapshot 예산으로 사전 계산하고 측정
- `/metrics` scrape가 game tick이나 IOCP worker lock을 기다리지 않을 것
- monitoring backend 장애가 게임서버 처리와 shutdown을 막지 않을 것

수치는 초기 목표이며 실제 baseline과 서버 사양을 기록한 뒤 확정한다.

### 20.2 검증 시나리오

1. 모니터링 비활성 Release baseline을 동일한 bot 부하와 시간으로 측정한다.
2. 상시 Counter/Gauge만 활성화하고 CPU, tick, throughput을 비교한다.
3. Stage와 PacketPool snapshot을 활성화하고 다시 비교한다.
4. Prometheus가 정상 주기, 1초 과도 scrape, 연결 실패 상태일 때 서버 영향을 확인한다.
5. Prometheus/Collector를 중단해도 서버가 block, retry 폭주, memory 증가 없이 실행되는지 확인한다.
6. 의도적으로 DB 지연, send backlog, PacketPool fail, tick overrun을 만들어 metric과 alert를 검증한다.

### 20.3 측정 도구

`Development/Monitoring/Measure-Monitoring.ps1`은 운영 daemon이 아니라 변경 후 성능·cardinality를 점검하는 수동 측정 도구다. 서버의 `/metrics`에 직접 요청해 target별 scrape 평균/p95/최대 시간, 최대 응답 byte, series/family 수와 같은 host의 서버 process CPU/peak memory를 JSON으로 기록한다.

- 기본 측정: 60초, 15초 간격, scrape p95 100ms 이하, target당 series 10,000개 이하
- 결과: `Development/Monitoring/results/monitoring-*.json`
- 1초 간격은 정상 운영 설정이 아니라 과도 scrape 스트레스 시험
- Prometheus가 실행 중이면 스크립트 요청과 실제 scrape가 동시에 발생하므로 측정 조건에 기록하거나 endpoint 단독 비용 측정 시 Prometheus를 중지한다.
- process CPU와 memory는 게임 로직을 포함한 전체 값이므로 같은 Release binary, bot 수, 시나리오, 시간의 baseline과 비교한다.
- 모니터링 비활성 상태에서는 `/metrics`가 열리지 않으므로 이 스크립트 하나만으로 비활성 baseline을 측정할 수 없다.

## 21. 구현 단계와 완료 조건

### 단계 1. 설계 확정

- 이 문서의 메트릭 이름, label, 수집 주기와 성능 목표를 검토한다.
- 완료 조건: 각 subsystem의 소유 thread와 snapshot 경로가 결정됨.
- 구현 상태: **완료.** 상시 metric, 저빈도 합계 snapshot, 요청 시 진단의 경계를 확정했다.

### 단계 2. 기존 통계 동시성 수정

- NetLibStats와 Stage user count hint를 안전하게 변경한다.
- 완료 조건: Debug x64 빌드와 관련 테스트 통과, Thread Sanitizer를 사용할 수 없는 Windows 환경에서는 반복 부하 테스트로 보완.
- 구현 상태: **완료.** NetLib 통계와 Stage user hint의 cross-thread 읽기 경로를 atomic snapshot으로 변경했다.

### 단계 3. 공통 Metrics 기반

- ServerBase에 metric registry, 내부 `/metrics` endpoint와 설정을 추가한다. subsystem snapshot은 각 계측 단계에서 registry에 발행한다.
- endpoint 실패와 backend 부재가 서버 동작에 영향을 주지 않게 한다.
- 완료 조건: 모든 서버가 공통 up/info/self metric을 노출하고 clean shutdown함.
- 구현 상태: **완료.** `/metrics`와 `/health` HTTP 200 응답 및 Debug x64 전체 빌드를 확인했다.

### 단계 4. NetLib, Session, PacketPool

- byte, packet, error, buffer, send queue, pool metric을 추가한다.
- 완료 조건: 송수신 부하에서 OS NIC 값과 방향·증가 추세가 일치하고 pool invariant가 성립함.
- 구현 상태: **완료.** Registry↔Gateway 실제 연결에서 양방향 byte/packet 증가, queue/in-flight/recv buffer의 0 복귀, disconnect 후 active session과 Session 객체 정리를 확인했다. OS NIC 비교와 Release 부하 비용 측정은 단계 9에서 수행한다.

### 단계 5. ContentsThread와 DB

- tick, overrun, task queue, DB queue/latency/error를 추가한다.
- 완료 조건: 인위적 sleep과 DB 지연에서 해당 metric과 alert 조건이 재현됨.
- 구현 상태: **핵심 계측 완료.** RegistryServer에서 50ms ContentsThread tick histogram 누적과 정상 종료를 확인했다. LoginServer의 실제 read-only 계정 조회에서 request/result 1건, queue wait와 execution histogram 기록, 완료 후 queue/active 0 복귀를 확인했다. 인위적 backlog·transaction retry·DB 장애 alert 검증은 단계 9의 fault injection 부하 테스트에서 수행한다.

### 단계 6. GameServer와 Stage

- Stage-owned snapshot과 게임 상태 metric을 추가한다.
- 완료 조건: 치트 또는 테스트 spawn/despawn 결과가 snapshot 개수와 일치하며 다른 thread가 Stage container를 직접 읽지 않음.
- 구현 상태: **핵심 계측 완료.** 각 Stage가 5초마다 owner thread에서 snapshot을 만들고 StageManager가 scrape 시 GameServer 전체 user/object/skill 효과/projectile/cast/buff/queue/async/sector 합계와 sector 최대값을 게시한다. Stage 식별 label과 `MetricScopeId`는 제거했으며 Debug x64 전체 빌드를 통과했다. 합계 전환 후 실제 user 입장·전투 중 값 일치와 비용 측정은 단계 9의 부하 시나리오에서 추가 검증한다.

### 단계 7. Gateway와 나머지 서버

- 인증, 라우팅, 서버 연결, 로그인, Registry, Communication metric을 추가한다.
- 완료 조건: 접속·중복 로그인·GameServer disconnect·cross-server 이동 시나리오의 결과가 metric에 반영됨.
- 구현 상태: **핵심 계측 완료.** Debug x64 전체 빌드와 Registry·Login·Gateway·Communication·GameServer 동시 기동으로 Registry 실행 서버 4개, Login↔Gateway 1개, Gateway↔Game 1개, Communication↔Game 1개 연결 gauge를 확인했다. 실제 client 인증, 중복 로그인, disconnect, reroute, chat/whisper 결과 counter와 비용은 단계 9 통합 부하 시나리오에서 추가 검증한다.

### 단계 8. 운영 도구와 dashboard

- native Windows metric, Prometheus/Collector, Grafana와 log agent를 구성한다.
- 완료 조건: 호스트 종료를 포함한 alert 테스트가 게임서버와 독립된 경로로 도착함.
- 구현 상태: **metric 운영 도구 구성 완료.** Windows native Prometheus와 Grafana 다운로드/기동 스크립트, 서버 내 Windows API process/host 수집, 15초 scrape 설정, 서버·Contents 합계·DB·network·Stage 합계·Windows의 14개 alert rule, 자동 provisioning되는 `MMO Server Overview` dashboard를 `Development/Monitoring`에 추가했다. `windows_exporter`와 Alertmanager는 사용하지 않으며 Grafana bundled Zipkin plugin은 Registry 내부 port 충돌 방지를 위해 비활성화한다. 중앙 log agent, host 종료 및 fault injection 경보 검증은 단계 9에서 확정한다.

### 단계 9. 성능 검증과 운영 기준 확정

- 동일 부하 A/B 테스트로 비용과 cardinality를 측정한다.
- 완료 조건: 성능 예산 충족, dashboard와 alert runbook 작성, Release 설정 확정.
- 구현 상태: **측정 기반, 초기 runbook, Release 빌드 완료.** `Development/Monitoring/Measure-Monitoring.ps1`이 endpoint별 scrape 응답 시간·byte·series/family cardinality와 서버 process CPU/peak memory를 JSON으로 기록한다. RegistryServer Debug 단독 1초 scrape smoke에서 10초 측정 p95 16.202ms, 309 series, 최대 28,010 bytes를 확인했고, 시간축 보정 후 3초/4회 재검증도 통과했다. 최신 소스로 `Release|x64` 전체 빌드 후 RegistryServer Release 단독 3초/4회 smoke도 p95 17.103ms, 309 series, 최대 27,993 bytes로 통과했다. 이 수치들은 부하 없는 도구 검증값이며 성능 판정에는 사용하지 않는다. 14개 alert의 진단 query와 초기 대응은 `Development/Monitoring/RUNBOOK.md`에 기록했다. 동일 DummyClient 부하의 모니터링 비활성/활성 A/B와 fault injection 경보 검증은 남아 있다.
