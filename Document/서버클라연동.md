# 로그인, 게임서버 접속

1. 클라가 로그인요청
로그인 씬에서 로그인서버에 LoginReq (id, password) 전송

2. 로그인 서버가 LoginReq 받음
AccountDB 에서 id, password 조회해서 검증, 인증토큰 발급 (8byte)
게이트웨이 서버에 LoginAuthTokenNtf (accountId, token, 만료시간) 전송
클라에게 LoginRes 전송 (성공, gatewayIP, port, accountId, authToken)

3. 게이트웨이서버가 LoginAuthTokenNtf 받음
pendingAuth map에 저장

4. 클라가 게이트웨이서버에 접속하여 GatewayAuthReq (accountId, authToken) 요청 

5. 게이트웨이서버가 GatewayAuthReq 받음
pendingAuth map에서 인증토큰 검증
게임서버 선택 (유저수 적은 곳 또는 이전 접속 캐시)
게임서버에 GatewayUserEnterNtf (accountId, gatewayId, clientIp) 전송

6. 게임서버가 GatewayUserEnterNtf 받음
DB에서 캐릭터 목록 로드
User 객체 생성 + map 등록
SystemStage(캐릭터선택용 스테이지)에 UserEnter push
클라에게 GameEnterNtf, CharacterListNtf(캐릭터 0~N개) 전송함

7. 클라가 GameEnterNtf 받음
지금은 하는일 없음

8. 클라가 CharacterListNtf 받음
현재 로그인 씬이기 때문에 CharacterListNtf 를 어딘가에 저장해두고 캐릭터선택 씬으로 이동함. 캐릭터선택 씬에서 CharacterListNtf 를 계속 처리함
캐릭터가 없으면 게임서버에 CharacterCreateReq 패킷으로 캐릭터생성 요청. 그러면 게임서버가 캐릭터 생성하고 CharacterCreateRes 보내줌
캐릭터가 있으면 CharacterSelectReq 패킷으로 캐릭터선택 요청

9. 게임서버가 CharacterSelectReq 받음
DB에서 캐릭터 로드, Character 객체 생성
User가 Character를 shared_ptr로 소유(주인), Character는 User를 weak_ptr로 참조
클라에게 CharacterSelectRes 전송 (캐릭터 전체 데이터 + stageDataKey)
  ※ 스폰 좌표는 여기서 안 보냄 — 좌표는 입장 완료 후 StageLoadCompleteRes로 전달 (좌표의 단일 출처)
유저를 Moving 상태로 두고, SystemStage에서 UserLeave push + 대상 스테이지(Town)에 UserEnter push
  ※ UserEnter 시점에는 유저만 입장하고 캐릭터 스폰은 미룬다 (2단계 입장)

10. 클라가 CharacterSelectRes 받음
캐릭터 전체 데이터를 데이터모델로 보관(영속, 스테이지 이동에도 유지) 후 게임 씬으로 이동
게임 씬 진입: 데이터모델로 LocalPlayer를 1회 생성하되 비활성(숨김) 상태로 둔다
맵/NavMesh 로딩 완료 후 게임서버에 StageLoadCompleteReq 전송
  ※ 캐릭터는 아직 화면에 안 보임. StageLoadCompleteRes를 받을 때 활성화된다

11. 게임서버가 StageLoadCompleteReq 받음
대상 스테이지가 캐릭터를 스폰한다 (도착 위치 결정 → Stage에 등록), 유저 상태를 InStage로 전환
클라에게 이 순서로 전송:
StageLoadCompleteRes(스폰 좌표/회전)  →  StatUpdateNtf  →  HpMpNtf  →  ObjectVisibilityNtf(주변 오브젝트)
  ※ StageLoadCompleteRes를 먼저 보내야 클라가 LocalPlayer를 활성화한 뒤 이어지는 Stat/Hp/Visibility를 처리할 수 있다

12. 클라가 StageLoadCompleteRes 받음
보관 중이던 LocalPlayer를 받은 좌표에 배치하고 활성화(조작 가능), 로딩 종료
뒤따라 온 Stat/Hp/Visibility로 스탯·주변 오브젝트를 반영하고 게임 플레이 시작

# 스테이지 이동

## 개요
- 한 게임서버 안의 다른 Stage(마을 ↔ 필드 등)로 캐릭터를 옮기는 흐름이다.
- 최초 입장(캐릭터 선택)과 **동일한 2단계 입장**(StageLoadCompleteReq → 스폰 → StageLoadCompleteRes)을 공유한다.
  차이는 트리거 패킷(StageMoveReq vs CharacterSelectRes)과 도착 위치 타입뿐이다.
- 캐릭터/스탯/버프는 새로 만들지 않고 그대로 유지된다.
  서버: User가 Character를 계속 소유하므로 이동 중에도 캐릭터가 살아있다.
  클라: LocalPlayer를 파괴하지 않고 숨김 → 재배치만 한다 (데이터모델은 영속).
- 도착 위치는 `StageStartPosition` 게임데이터로 정한다. (StageKey, StagePositionType) 조합으로 좌표를 조회한다.

## 퇴장(이동) 가능 검사 — 공통 가드
- 캐릭터가 현재 Stage에서 빠져나가는 모든 흐름(스테이지 이동 / 게임 중 캐릭터 선택 복귀)은 **퇴장 전에 동일한 방어 검사**를 거쳐야 한다. `Stage::canLeaveStage` 함수로 검사함
- 검사 항목 (모두 통과해야 퇴장 허용):
  1. **유저 상태 == InStage**: Moving(전환 중)/None(미입장)이면 거부. 전환 중 중복 요청 방지.
  2. **캐릭터가 이 Stage 소속**: `GetCurrentCharacter()`가 있고 `GetStage() == this` (없거나 다른 Stage면 거부).
  3. **진행 중인 DB 코루틴 후속작업 없음**: `Character::HasPendingAsync() == false`. async(인벤/저장 등) 진행 중이면 거부 → 그 후속작업이 같은 Stage 단일 스레드에서 완결되도록 보장(AsyncPin 수명게이트와 한 쌍, 게임서버.md 참조). 검사 실패시 클라는 재시도 해야함.
- 스테이지 이동은 여기에 더해 **이동 전용 검증**도 한다: position_type 유효성, 목적지 Stage 존재/단일 인스턴스/이동가능 타입(Town·Field), 도착 위치(StageStartPosition) 데이터 존재.
- 호출처: `Stage::handleStageMoveReq`, `Stage::handleReturnToCharacterSelectReq` (둘 다 **Stage 컨텐츠 스레드**에서 실행되므로 캐릭터/Stage 소유 상태를 데이터레이스 없이 검사한다 — 그래서 이 흐름들은 GameServer 스레드가 아니라 User 패킷큐를 통해 Stage가 처리하도록 둔다).

## 동일 서버 내 이동 흐름

1. 클라가 StageMoveReq 전송
StageMoveReq 패킷 내용: target_stage_data_key(목적지 Stage 데이터 Key), position_type(EStagePositionType), target_game_server_id(=0: 현재 서버)
전송 직후 사용자입력을 잠금하고 로딩 대기 상태로 둔다

2. 게임서버(현재 Stage)가 StageMoveReq 받음
요청 내용을 검증한다(위 "퇴장 가능 검사 canLeaveStage" + 이동 전용 검증). 검증 실패 시 StageMoveRes(실패, 사유) 전송하고 종료
검증 통과 시:
  · 유저를 Moving 상태로 두고 도착 position_type 보관
  · 현재 Stage에서 퇴장(컨테이너/sector에서 제거 + 주변 유저에게 despawn 브로드캐스트). 캐릭터는 User가 계속 소유하므로 파괴되지 않음
  · 목적지 Stage에 유저만 입장시킴(캐릭터 스폰은 미룸)
  · 클라에게 StageMoveRes(성공, target_stage_data_key) 전송

3. 클라가 StageMoveRes 받음
실패면 사유를 표시하고 이동 취소(사용자입력을 잠금 해제)
성공이면 로딩 시작: LocalPlayer 숨김 → 원격 오브젝트(타 캐릭터/몬스터) 제거 → 목적지 NavMesh/맵 프리팹 교체 → 게임서버에 StageLoadCompleteReq 전송

4. 게임서버(목적지 Stage)가 StageLoadCompleteReq 받음
캐릭터를 스폰: position_type으로 StageStartPosition 좌표를 조회(NavMesh 스냅 보정) → Stage에 등록, 유저 상태를 InStage로 전환
클라에게 이 순서로 전송:
StageLoadCompleteRes(스폰 좌표/회전)  →  StatUpdateNtf  →  HpMpNtf  →  ObjectVisibilityNtf(주변 오브젝트)

5. 클라가 StageLoadCompleteRes 받음
숨겨둔 LocalPlayer를 받은 좌표에 배치하고 활성화(조작 가능), 로딩 종료
뒤따라 온 Stat/Hp/Visibility로 반영하고 게임 플레이 재개

## 크로스 서버 이동 (DB 경유, 구현됨)
- StageMoveReq의 target_game_server_id가 다른 서버를 가리키면 크로스 서버 이동이다.
- **DB 경유 방식**으로 구현되어 있다. 동일 서버 이동과 **동일한 2단계 입장**(StageLoadCompleteReq → 스폰 → StageLoadCompleteRes)을 그대로 공유하므로 **클라 코드는 동일**하며, 클라는 서버가 바뀐 것을 모른다.
- 흐름:
  1. 출발 서버(현재 Stage)가 StageMoveReq(크로스서버) 받음 → 검증 → 유저를 Moving 으로 두고 현재 Stage에서 퇴장.
  2. 출발 서버가 캐릭터를 DB에 저장(UPDATE) → 게이트웨이에 UserMoveToGameServerReq 전송 → 출발 서버의 글로벌 유저맵에서 제거.
  3. 게이트웨이가 유저 라우팅을 목적지 서버로 변경(routedGameServerId) → 목적지 서버에 GatewayUserRerouteNtf 전송.
  4. 목적지 서버가 DB에서 캐릭터를 로드해 User/Character 생성 → 대상 Stage에 유저 입장(Moving) → **클라에 StageMoveRes(성공) 전송**. (성공 응답을 목적지 서버가 보내는 점만 동일 서버 이동과 다름)
  5. 이후는 동일 서버 이동의 로딩~스폰(위 3~5단계)과 동일. 클라의 StageLoadCompleteReq 는 게이트웨이가 목적지 서버로 라우팅한다.
- v1 제약:
  - HP/MP/버프/쿨다운 등 휘발성 상태는 Character proto 에 저장되지 않아 이동 시 직업기본 최대치로 리셋된다(캐릭터 재선택과 동일).
- 실패 처리:
  - **저장/게이트웨이 통보 실패(commit 이전)**: 유저를 출발 Stage에서 떠나보내기 전에 저장하므로(퇴장을 성공 후로 미룸), 실패하면 InStage 로 복귀하고 StageMoveRes(실패)만 보낸다 → **무소속 유저가 생기지 않는다.** ("유저는 반드시 Stage에 속한다" 불변식 유지)
  - **commit 이후 실패(설계 단계)**: 게이트웨이가 목적지 서버를 못 찾거나 목적지에서 Stage 를 못 찾는 경우의 복귀(원/목적지 오픈필드)는 아직 미구현.

## 관련 파일
- 서버(동일 서버): `Stage.cpp`(handleStageMoveReq / handleStageLoadCompleteReq), `User`(상태머신 + 캐릭터 소유)
- 서버(크로스 서버): `GameServer.cpp`(BeginCrossServerMove / handleGatewayUserReroute / saveCharacterToDB / loadCharacterForUser), `GatewayServer.cpp`(handleUserMoveToGameServer 재라우팅)
- 클라: `StageManager.cs`(RequestStageMove / onStageMoveRes / BeginStageLoad / onStageLoadCompleteRes), `CharacterDataCache.cs`(캐릭터 데이터 영속)
- 데이터: `StageStartPosition`(도착 좌표), `EStagePositionType`(enum)
- 패킷: StageMoveReq/Res, StageLoadCompleteReq/Res, (서버간) UserMoveToGameServerReq / GatewayUserRerouteNtf
- 치트: `stage <stageKey> [serverId]` (serverId 지정 시 크로스서버 이동)


# 캐릭터 선택으로 복귀 (게임 중)
- 게임 플레이 중(Esc 메뉴 "캐릭터 선택으로") 캐릭터 선택 화면으로 돌아가는 흐름. 스테이지 이동의 "퇴장" 골격을 공유하되, 목적지가 SystemStage(캐릭터 선택창)이고 **캐릭터를 스폰하지 않는다**(플레이 종료 → 선택 상태 None).
- 흐름:
  1. 클라가 ReturnToCharacterSelectReq 전송. 이 패킷은 GameServer가 직접 처리하지 않고 게임플레이 패킷처럼 User 큐로 흘러 **현재 Stage가 처리**한다(`Stage::handleReturnToCharacterSelectReq`). → 스테이지 이동과 같은 스레드/가드(canLeaveStage)를 공유하기 위함.
  2. 현재 Stage: `canLeaveStage` 통과 시 → 상태 None으로 되돌리고 현재 Stage 퇴장(OnUserLeave, 주변 despawn) → SystemStage에 UserEnter enqueue.
  3. **`SystemStage::OnUserEnter`가 CharacterListNtf를 전송**한다.
  4. 클라가 CharacterListNtf를 받으면 캐시 갱신 + CharacterSelection 씬으로 전환. (별도 Res 없음 — 목록 수신이 성공 신호)
- **CharacterListNtf 전송 일원화**: 로그인 최초 입장과 캐릭터선택 복귀 둘 다 `SystemStage::OnUserEnter` → `GameServer::SendCharacterListForUser` **한 경로**로 전송한다(전송 시점 = SystemStage 입장).
  - DB 로드 코루틴의 후속작업(전송)은 SystemStage의 `GetResumeExecutor()`를 넘겨 **SystemStage 컨텐츠 스레드에서 재개**한다(IOCP 재개 금지 — 코루틴 후속작업 스레드 일관성, 게임서버.md 참조).
- 관련 파일: 서버 `Stage.cpp`(handleReturnToCharacterSelectReq / canLeaveStage), `SystemStage.cpp`(OnUserEnter). 클라 `GameScene.cs`(Esc 메뉴 → requestReturnToCharacterSelect). 패킷 ReturnToCharacterSelectReq

# 채팅 시스템

채팅의 기준 문서다. 클라이언트는 GameServer와 직접 연결하지 않고 기존 게임 패킷 경로인 `Client ↔ GatewayServer ↔ GameServer`를 사용한다. GameServer 사이의 전체 채팅과 귓속말 라우팅은 단일 `CommunicationServer`가 담당한다.

## 채팅 범위

| `ChatType` | 수신 범위 | 처리 위치 |
|---|---|---|
| `StageChannel` | 같은 Stage와 Channel의 `InStage` 유저 | 현재 `Stage`의 `m_users` |
| `GameServer` | 같은 GameServer의 모든 `InStage` 유저 | `ChatManager`가 글로벌 유저 맵 순회 |
| `Global` | 연결된 모든 GameServer가 보유한 유저 | `CommunicationServer` fan-out 후 각 `ChatManager`가 전달 |
| `Whisper` | 캐릭터 이름으로 지정한 활성 캐릭터 1명 | `CommunicationServer`가 대상 GameServer를 찾고 해당 `ChatManager`가 전달 |

Stage 인스턴스 하나가 한 채널을 나타내므로 `StageChannel`은 현재 Stage의 유저만 순회하면 Stage와 Channel 범위를 동시에 만족한다. GameServer가 클라이언트로 패킷을 보낼 때는 수신 계정을 Gateway별로 묶는 기존 `PacketSender` 경로를 사용한다.

## 클라이언트 패킷

| ID | 패킷 | 방향 | 용도 |
|---:|---|---|---|
| 3001 | `ChatSendReq` | Client → GameServer | 채팅 종류, 메시지, 귓속말 대상 이름 전송 |
| 3002 | `ChatRecvNtf` | GameServer → Client | 송신 캐릭터 ID·이름과 메시지 수신 |
| 3003 | `ChatSendRes` | GameServer → Client | 현재 귓속말 성공 echo와 전송 실패 사유 전달 |

`ChatSendReq.target_name`은 `Whisper`에서만 사용한다. 클라이언트 명령 형식은 `/w 캐릭터이름 메시지`이며, 송신자의 Character ID와 이름은 클라이언트 값이 아니라 GameServer가 보유한 현재 `Character` 데이터로 채운다.

## 서버 내부 패킷

| ID | 패킷 | 방향 | 용도 |
|---:|---|---|---|
| 3001 | `ChatBroadcastReq` | GameServer → CommunicationServer | 전체 채팅 요청 |
| 3002 | `ChatBroadcastNtf` | CommunicationServer → GameServer | 전체 채팅 fan-out |
| 3003 | `ChatPresenceNtf` | GameServer → CommunicationServer | 현재 선택된 활성 캐릭터 등록·해제 |
| 3004 | `WhisperReq` | GameServer → CommunicationServer | 캐릭터 이름 기반 귓속말 요청 |
| 3005 | `WhisperNtf` | CommunicationServer → 대상 GameServer | 대상 캐릭터에게 귓속말 전달 |
| 3006 | `WhisperRes` | CommunicationServer → 송신 GameServer | 라우팅 성공·실패 결과 |

CommunicationServer가 GameServer의 내부 서버 포트에 연결하는 방향이다. 연결 직후 handshake로 서버 종류와 ID를 검증하며, GameServer는 handshake가 완료된 단일 CommunicationServer 세션만 채팅 내부 패킷의 송수신 경로로 인정한다.

## GameServer 책임 분리

- `GameServer`는 내부 서버 accept/recv/disconnect, CommunicationServer handshake·Registry 검증과 세션 생명주기를 담당한다. 이 연결은 향후 다른 소셜 기능도 공유할 수 있으므로 채팅 도메인에 포함하지 않는다.
- `ChatManager`는 GameServer 범위 채팅, 글로벌 채팅 요청·수신, 귓속말 요청·수신·결과, 활성 캐릭터 presence와 재연결 snapshot을 담당한다. 글로벌·귓속말 수신자는 Stage 상태를 검사하지 않으며, 내부 채팅 패킷 dispatcher는 인증된 연결에서 받은 메시지를 `ChatManager`에 위임한다.
- `StageChannel` 채팅은 Stage의 단일 스레드와 `m_users`에 종속되므로 `Stage`에 남는다. Stage는 나머지 채팅과 캐릭터 선택 화면 복귀 시의 presence 해제를 `GameServer::GetChatManager()`로 호출하고, 선택·접속 종료·크로스서버 handoff의 presence 변경은 `GameServer`가 처리한다.

## 전송 흐름

### Stage·GameServer 채팅

1. `Stage::handleChatSendReq`가 송신자의 현재 캐릭터, `InStage` 상태, 현재 Stage 소속 여부와 메시지를 검증한다.
2. `StageChannel`은 현재 Stage의 `InStage` 계정을 수집해 `ChatRecvNtf`를 보낸다.
3. `ChatManager`는 글로벌 유저 맵에서 같은 서버의 `InStage` 계정을 수집해 `ChatRecvNtf`를 보낸다.
4. 송신자도 수신 범위에 포함되므로 자신이 보낸 메시지를 같은 알림 경로로 표시한다.

### 전체 채팅

1. 송신 GameServer가 인증된 단일 CommunicationServer 세션에 `ChatBroadcastReq`를 보낸다.
2. CommunicationServer는 연결된 모든 GameServer에 `ChatBroadcastNtf`를 fan-out한다.
3. 각 GameServer의 `ChatManager`는 글로벌 유저 맵에 있는 모든 계정에 `ChatRecvNtf(Global)`을 보낸다. `Moving`과 `None`도 수신 대상이다.

### 귓속말과 presence

1. 캐릭터 선택이 확정되거나 크로스서버 목적지에서 캐릭터 로드가 끝나면, Stage 로딩 완료 전이라도 GameServer가 `ChatPresenceNtf(online=true)`를 보낸다.
2. 같은 GameServer 안에서 Stage를 이동할 때는 presence를 유지한다. 캐릭터 선택 화면 복귀·로그아웃·크로스서버 출발 handoff 확정 때 `online=false`를 보낸다.
3. CommunicationServer는 Gateway ID를 알지 않으며 `characterName → { characterId, gameServerId }` presence만 보관한다.
   - `online=false`는 현재 저장된 Character ID와 GameServer ID가 모두 일치할 때만 제거한다. 캐릭터가 다른 GameServer에 새로 등록된 뒤 이전 서버의 해제 패킷이 늦게 도착해도 새 presence를 지우지 않는다.
4. `/w` 요청을 받은 CommunicationServer는 대상 이름의 presence를 찾아 해당 GameServer 한 곳에만 `WhisperNtf`를 보낸다.
5. 대상 GameServer는 Character ID로 글로벌 유저 맵의 계정을 찾고, `InStage` 여부와 무관하게 `User`가 가진 Gateway 경로로 `ChatRecvNtf(Whisper)`를 전달한다.
6. CommunicationServer는 성공·실패를 `WhisperRes`로 송신 GameServer에 돌려주고, GameServer는 송신 클라이언트에 `ChatSendRes`를 보낸다.

수신자는 `[귓속말]`, 송신자는 성공 응답을 `[귓속말 → 대상]`으로 표시한다. 대상이 없거나 오프라인이거나 CommunicationServer를 사용할 수 없으면 송신자에게 `[시스템]` 메시지로 실패 사유를 표시한다.

## CommunicationServer 재연결

- GameServer의 `ChatManager`는 CommunicationServer 연결 여부와 무관하게 현재 선택된 활성 캐릭터 presence를 로컬 thread-safe 맵에 유지한다.
- CommunicationServer 연결이 끊기면 해당 GameServer ID로 등록된 presence를 CommunicationServer에서 모두 제거한다.
- CommunicationServer가 GameServer에 다시 연결해 handshake를 마치면, `GameServer`가 handshake 응답을 보낸 뒤 `ChatManager`에 현재 presence snapshot 일괄 전송을 위임한다.
- snapshot 전송 중 presence 변경은 같은 맵 잠금 뒤에 처리되므로 최신 변경 패킷이 snapshot보다 나중에 전달된다. 재연결 후 별도 Stage 이동 없이 귓속말 라우팅이 복구된다.

## 검증 규칙과 오류 표시

- 송신자는 현재 Character를 선택했고 `InStage`이며 요청을 처리하는 Stage에 속해야 한다.
- 메시지는 비어 있지 않고 UTF-8 기준 256 bytes 이하여야 한다. 클라이언트도 전송 전에 같은 바이트 제한을 검사한다.
- 잘못된 `/w` 형식, 바이트 제한 초과, 게임서버 연결 없음은 클라이언트가 로컬 `[시스템]` 메시지로 표시한다.
- CommunicationServer와 GameServer는 내부 세션 handshake, 메시지 크기, 캐릭터·계정 ID를 다시 검증한다.
- 현재 캐릭터 이름은 전역에서 유일하다고 가정한다. 이름 중복 생성 방지는 캐릭터 생성·DB 제약 단계에서 처리해야 한다.

## 클라이언트 HUD와 입력 규칙

- `UI_Chat`은 최근 50개 메시지를 보관하고, `UI_ChatLine`은 메시지 한 줄의 TMP 표시와 페이드를 담당한다.
- 메시지는 채팅 종류별 색상과 수신 시각을 표시한다. 평소에는 10초 표시 후 2초 동안 페이드아웃한다.
- Enter로 채팅창과 입력 포커스를 열고 Esc로 닫는다. 채팅창이 열린 동안 첫 Esc는 입력 포커스 여부와 관계없이 채팅창만 닫고 게임 메뉴를 열지 않는다.
- 채팅창이 열려 있어도 키보드 게임 입력은 TMP 입력 칸에 실제 포커스가 있을 때만 차단한다. 마우스 이동은 포커스 여부와 관계없이 유지하되 입력창·채널 버튼·스크롤 영역 위의 클릭은 UI가 소비한다.
- 포커스가 없는 열린 채팅창에서 Enter를 누르면 입력 칸에 다시 포커스를 준다.
- 입력 중에는 최근 로그를 펼치고 휠·드래그 스크롤과 자동 숨김 스크롤바를 활성화한다. 사용자가 최신 메시지를 보고 있을 때만 새 메시지를 자동 추적한다.

## 회귀 테스트 체크리스트

- 같은 Stage·Channel, 같은 GameServer, 서로 다른 GameServer의 전체 채팅이 각각 정해진 범위에만 한 번씩 전달되는지 확인한다.
- 같은 GameServer와 다른 GameServer의 귓속말에서 수신자는 `[귓속말]`, 송신자는 `[귓속말 → 대상]` 한 줄씩 받는지 확인한다.
- 같은 GameServer의 Stage 이동 로딩 중인 유저가 글로벌 채팅과 귓속말을 수신하는지 확인한다.
- 오프라인·미존재 대상과 CommunicationServer 중단 상태에서 송신자에게 해당 `[시스템]` 실패 사유가 표시되는지 확인한다.
- CommunicationServer 재시작 후 Stage 이동 없이 presence snapshot과 귓속말이 복구되는지 확인한다.
- CommunicationServer 중단 중 대상이 Stage 이동·로그아웃한 뒤 재시작했을 때 snapshot에 최종 상태만 반영되는지 확인한다.
- `/w`, `/w 이름`, UTF-8 256 bytes 초과 입력이 전송되지 않고 로컬 시스템 안내를 표시하는지 확인한다.
- 채팅창 포커스, Enter·Esc, 게임 키보드·마우스 이동, 과거 로그 스크롤이 "클라이언트 HUD와 입력 규칙"대로 동작하는지 확인한다.

## 현재 운영 제약과 관련 파일

- CommunicationServer는 한 대만 존재한다. 글로벌 채팅은 인증된 단일 CommunicationServer 세션을 전제로 한다.
- CommunicationServer는 Gateway ID를 보관하지 않는다. 글로벌·귓속말의 클라이언트 전송은 대상 GameServer가 `User`의 Gateway ID를 사용해 처리한다.
- 크로스서버 이동에서 출발 presence 해제 후 목적지 캐릭터 등록 전까지의 짧은 공백에는 글로벌 채팅·귓속말 수신을 보장하지 않는다. 후속 개선 사항이다.
- 계정별 채팅 rate limit, 차단·신고·금칙어와 캐릭터 이름 중복 방지는 아직 구현하지 않았다.
- 프로토콜: `Development/Server/PacketGenerator/Proto/GamePacket/chat_packet.proto`, `ServerPacket/chat_server_packet.proto`
- 서버: `Development/Server/GameServer/GameServer.cpp/.h`, `GameServer/Managers/ChatManager.cpp/.h`, `GameServer/Stages/Stage.cpp`, `CommunicationServer/CommunicationServer.cpp/.h`
- 클라이언트: `Development/Client/Assets/Scripts/Game/UI_Chat.cs`, `Scripts/UI/UI_ChatLine.cs`

# 캐릭터 스탯의 연동
1. 게임서버가 CharacterSelectReq 받으면 캐릭터를 생성하고, 캐릭터에게 스탯을 적용한다. 그리고 클라에게 CharacterSelectRes 를 보낸다.
2. 게임서버에서 캐릭터가 Stage에 스폰(입장 완료)되면 이 순서로 클라에게 패킷을 보낸다:
StageLoadCompleteRes(입장 완료 + 스폰 좌표)  →  SendStatUpdateNtf(캐릭터의 모든 스탯)  →  SendHpMpNtf(캐릭터의 현재 HP/MP)
  ※ StageLoadCompleteRes를 먼저 보내야 클라가 그 시점에 LocalPlayer를 활성화/배치하고, 이어 도착한 Stat/Hp를 그 캐릭터에 적용할 수 있다 (과거엔 StageEnterNtf가 마지막이었으나 2단계 입장으로 순서가 바뀜)
3. 클라가 SendStatUpdateNtf 를 받으면 캐릭터의 스탯을 받은것으로 교체하고, SendHpMpNtf 를 받으면 캐릭터의 현재 HP/MP를 받은것으로 교체한다.
4. 이후 서버에서 스탯에 변경사항이 있으면 클라에게 SendStatUpdateNtf 를 보내고, 현재 HP/MP 변경사항이 있으면 SendHpMpNtf 를 보낸다.

	- 스테이지이름.bin.navmeta.json 파일 (NavMesh 메타파일. 월드크기 등의 정보가 있음)
- 출력경로:
   - 클라이언트 : Client/Assets/StreamingAssets/NavMesh/

├─ Visual/                          ← MeshRenderer 있음. NavMeshSource 없음.
│  ├─ Terrain_Detailed              (고폴리 지형)

│  ├─ Rocks, Props                  (소품)
│  ├─ Buildings_Exterior            (건물 외관, 디테일)
│  └─ Particle Effects, VFX
│
└─ Navigation/                      ← MeshRenderer 끄거나 에디터 전용. NavMeshSource 부착.
   ├─ Walkable_Floor_Plane          (단순한 바닥 메시. 캐릭터가 걸을 수 있는 영역)
   ├─ Walkable_Stairs_Ramp          (계단 대신 ramp)
   ├─ Blocker_Invisible_Wall_01     (보이지 않는 벽. 길막기용)
   ├─ Blocker_Invisible_Wall_02
   ├─ Blocker_Cliff_Edge            (절벽 떨어짐 방지)
   └─ Building_Collision_Simple     (건물의 단순화된 콜리전 = navmesh source)

# 버프(Buff) 시스템

## 원칙
- **서버 권위**: 적용/해제/만료/스택/주기효과(DoT·HoT)는 전적으로 서버가 처리한다.
- **클라는 표시만**: 클라는 버프를 계산하지 않고, 서버가 내려준 정보(키/스택/남은시간/카테고리)를 UI로 보여줄 뿐이다. 
- **현재 버프 구현범위**: 스탯 수정 버프 + DoT/HoT(주기 HP 변동). 시전자별 독립 스택은 미지원(액터당 buffKey 1인스턴스).

## 패킷 (서버 → 클라 전용)
버프 패킷은 **UI 뱃지 정보만** 나른다. 실제 효과는 기존 패킷을 재사용한다:
- **스탯 변화** → 기존 `StatUpdateNtf`(합성 스탯 스냅샷)
- **HP 변화(DoT/HoT)** → 기존 `HpMpNtf`

| 패킷 | ID | 내용 | 용도 |
| --- | --- | --- | --- |
| `BuffNtf` | `GAME_PACKET_ID_BUFF_NTF`(7001) | object_id, buff_key, stack_count, remain_time_ms | 버프 추가/갱신(upsert). 같은 (object_id, buff_key) 면 갱신 |
| `BuffRemoveNtf` | `GAME_PACKET_ID_BUFF_REMOVE_NTF`(7002) | object_id, buff_key | 만료/디스펠/정리 공통 제거 |
| `BuffSnapshotInfo` | ObjectVisibilityNtf 에 내장됨 | buff_key, stack_count, remain_time_ms | 시야 진입 시 `CharacterSpawnInfo`/`MonsterSpawnInfo`의 `repeated buffs` 로 현재 버프 동봉 |

- `remain_time_ms = -1` 이면 영구(클라는 카운트다운 표시 안 함).

## 게임데이터 (`GameData_Buff`)
- enum 3종: `EBuffCategory`(Buff/Debuff), `EBuffStackPolicy`(Refresh/Stack/Ignore), `EPeriodicEffect`(DamageHp/HealHp)
- 주요 컬럼: `DurationMs`(-1=영구), `MaxStack`, `StackPolicy`, `TickIntervalMs`(0=주기효과 없음), `PeriodicType`/`PeriodicValue`(flat), `Stat1~3`/`StatValue1~3`(스택당 적용값)
- **스탯은 구성요소 스탯(`*Add`/`*AddPct`/`*Amp`/`*Reduce`)에만 넣는다.** `*Total`은 서버가 자동 재계산하므로 직접 넣지 않는다.
- `Category`/`Name`/`Desc`/`DurationMs`/`MaxStack`/`IconId` 는 클라에도 출력(UI용). 그 외(StackPolicy, Stat 등)는 서버 전용.

## 서버 구조
- `ActorObject` 가 `BuffComponent` 를 멤버로 소유 (Character/Monster 공통).
- `BuffComponent` API: `ApplyBuff(buffKey, casterObjectId)`, `RemoveBuff(buffKey)`, `Update(deltaMs)`, `OnOwnerDead()`, `OnOwnerStageChange()`.
- 스탯 적용은 `ActorObject::GetStatComponent()->ApplyStat/RemoveStat` (Amp/Reduce 비선형 때문에 스택마다 1회씩).
- 변화 통지 훅: `OnStatsChangedByBuff()`(Character→`StatUpdateNtf`), `OnHpChangedByBuff()`(Character→`HpMpNtf`). 몬스터는 no-op.
- 뱃지 송신: `Stage::BroadcastBuffNtf/BroadcastBuffRemoveNtf` 가 AOI(주변+본인) 유저에게 `GameServer::SendBuffNtf/SendBuffRemoveNtf` 로 전송.
- 시간 처리: 절대시각이 아니라 **남은시간/틱누적** 모델. `Update(deltaMs)` 의 deltaMs 가 틱 간격보다 커도(오브젝트 주기가 길어도) 그 사이 놓친 주기효과 틱을 보정해 발사.

## 클라 구조
- `ActorObject`/`MonsterObject` 가 `BuffHolder Buffs` 보유 (서버가 준 키/스택/남은시간 보관).
- `StageManager` 가 `BuffNtf`/`BuffRemoveNtf` 핸들러 등록 + spawn 스냅샷의 buffs 반영.
- UI: `UI_BuffBar`(Game 어셈블리, `UI_Scene`)가 `LocalPlayer.Buffs` 를 읽어 `UI_BuffIcon`(UI 어셈블리, SubItem) 을 생성/갱신/제거.

## 전체 흐름
```
[서버] ApplyBuff / 스택 / 만료 / 주기틱
   ├─ 스탯 변화      → StatUpdateNtf ─→ [클라] StatHolder
   ├─ HP 변화(DoT/HoT) → HpMpNtf      ─→ [클라] CurHp
   └─ 뱃지(키/스택/시간) → BuffNtf/BuffRemoveNtf (+spawn 스냅샷) ─→ [클라] BuffHolder → 버프 바
```

## 현재버전 기본 정책
- 시전자가 죽거나 떠나도 이미 걸린 버프는 유지.
- 스택 정책: Refresh(시간만 갱신) / Stack(스택+1, MaxStack까지) / Ignore(이미 있으면 무시).
- 진입점: 스킬·전투 등에서 `actor.GetBuffComponent().ApplyBuff(buffKey, casterObjectId)` 호출.

## netdelay 네트워크 지연 시뮬레이션 치트 상세내용
클라 콘솔에서 입력한 `netdelay` 명령은 등록된 클라치트가 아니므로 `CheatReq` 로 서버에 전송되고, 게임서버 `CheatManager::cheatNetDelay` 가 처리한다. **치트 친 본인 클라 연결에만** 인위적 네트워크 지연을 건다(다른 유저·서버 간 통신은 영향 없음).

`netdelay <recvMs> [sendMs]`

- `recvMs`: 클라→서버 수신 지연(ms). `sendMs`: 서버→클라 송신 지연(ms, 생략 시 recvMs 와 동일). 체감 RTT ≈ recvMs + sendMs.
- 예: `netdelay 100 100`(왕복 ≈ 200ms), `netdelay 50`(수신·송신 각 50ms), `netdelay 0 0`(지연 해제).

### 동작 경로
1. 게임서버 `CheatManager::cheatNetDelay`: 치트 친 유저의 `accountId`, `gatewayId` 를 알아내 `SetClientLatencyReq{account_id, recv_delay_ms, send_delay_ms}` 를 그 게이트웨이로 전송(`GameServer::SendToGateway`).
2. 게이트웨이 `handleSetClientLatency`: 해당 유저의 클라 Session 을 찾아 `ISession::SetSimulatedDelay(recvMs, sendMs)` 적용.
3. 실제 지연은 NetLib Session 에서 처리한다(클라는 게이트웨이에 붙으므로 지연도 게이트웨이의 클라 Session 에 건다).

### NetLib 지연 메커니즘 (참고)
- 지연은 **Session 단위**(`SetSimulatedDelay`)로 건다. 수신은 `OnRecv` 호출을, 송신은 `Send` 를 각각 delay 만큼 미룬다.
- IOCP 워커를 막지 않기 위해, 지연 패킷은 IoContext 의 **지연 스케줄러 스레드**(전용 1개)에 deliver 시각으로 예약했다가 그 시각에 직렬 처리한다(같은 세션 순서 보존).
- 지연이 0 이면 핫패스에서 **atomic 플래그 1개**(`m_sendDelayActive`/`m_recvDelayActive`)만 검사하고 곧장 처리 — 평상시 추가비용 없음.
- 런타임에 지연을 **줄여도 순서가 보존된다**: 대기 중인 지연 패킷이 남아있는 동안은 새 패킷도 파이프에 줄세우고(세션 단조 deliver 시각으로 클램프), 파이프가 비어야 fast path 로 복귀한다.

## dbgstat / dbgmon 디버그 UI 치트 상세내용
정상 플레이 중에는 받지 않는 서버측 정보를 보기 위한 개발용 디버그 HUD(`DebugHud.cs`, F9 토글)의 구독 토글 치트다. **구독은 별도 요청 패킷 없이 기존 치트 경로(`CheatReq`)를 그대로 쓴다.** 구독 상태는 치트 친 유저(`User`)에 보관되고(`_DEBUG` 한정 필드), `Stage::sendDebugSubscriptions`가 디버그 tick(약 100ms)마다 구독자에게 NTF를 push한다. 서버측 처리 경로는 전부 `_DEBUG` 게이팅(치트 수신·`User` 필드·송신 모두), 클라 `DebugHud`는 `UNITY_EDITOR || DEVELOPMENT_BUILD` 게이팅이라 라이브 빌드에는 들어가지 않는다.

### 디버그 패킷
- `DebugStatNtf`: 선택 오브젝트(몬스터, 캐릭터 등)의 전체 스탯 스냅샷. 클라는 `EStat` 전체를 순회하며 미수신 항목은 0으로 표시.
- `DebugMonsterPositionsNtf`: 내 캐릭터 주변 섹터(AOI)의 몬스터 서버 좌표 목록. 서버의 sector 컨테이너에서 직접 수집하므로 가시성 파이프라인(`ObjectVisibilityNtf`)과 무관한 "서버 진실"이다 → 클라가 들고 있는 몬스터 집합과 대조하면 스폰/가시성 버그를 잡을 수 있다.

### 기능별 동작
- `dbgstat <objectId>`: `CheatManager::cheatDbgStat`이 대상 유효성(이 Stage에 존재)을 확인하고 `User::SetDebugStatTarget`에 보관. HUD는 `DebugStatNtf`를 받아 raw/합성 스탯 목록을 표시.
- `dbgmon [on|off]`: `CheatManager::cheatDbgMon`이 `User::SetDebugMonsterPos` 토글. HUD는 `DebugMonsterPositionsNtf`를 받아 각 몬스터 서버 위치에 와이어프레임 큐브를 그린다(색/크기 조절 가능). 클라에 없는 몬스터는 빨강 `NO-CLIENT`, 있는 몬스터는 렌더 위치와의 오차 `Δ거리`를 표시.

### 설계 근거 (이미 있는 것은 재사용)
AOI 내 오브젝트의 합성 최종 스탯/버프 뱃지/위치는 클라가 이미 `StatUpdateNtf`/`BuffNtf`/`SnapshotNtf`로 받아 보관 중이다(`ActorObject.Stats`/`Buffs`). 그래서 디버그 패킷은 그것만으로는 알 수 없는 정보(선택 대상 전체 스탯, 가시성 파이프라인과 무관한 서버 권위 몬스터 위치)만 추가로 나른다. 버프 보기는 새 패킷 없이 대상의 `BuffHolder`를 그대로 표시한다.
