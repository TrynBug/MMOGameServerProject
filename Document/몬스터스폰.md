# 디아블로4 몬스터 스폰 시스템 설계 — 하이브리드(존 밀도 + 기획자 앵커)

> **상태: 설계 v1 (미구현).** 현재 코드에는 단건 `Stage::SpawnMonster`/`DespawnMonster` 와 사망→시체→디스폰만 있고, **스포너·리스폰·밀도·팩(무리)** 은 전혀 없다. 이 문서는 그 위에 얹을 스폰 시스템을 설계한다.

> 범위(v1): **기본 리스폰 + 팩(무리) 스폰**. 엘리트/챔피언 affix, 월드이벤트/surge, 난이도·파티 밀도 스케일링, 팩 어그로 전파는 **나중**.
> 전제: 단건 스폰 경로(`Stage::SpawnMonster` — NavMesh 스냅 + sector 등록 + AOI 통보), 사망·시체·디스폰(`updateMonsters` 의 corpse 만료 → `DespawnMonster`), 몬스터 FSM/스킬/스폰앵커·리쉬(`Monster`/`MonsterCombatComponent`)는 **유지·재사용**한다.
> 핵심 결론을 먼저: **신규 패킷은 0개.** 스폰은 전적으로 서버 내부 사건이고, 클라는 이미 있는 가시성 패킷(`ObjectVisibilityNtf`/`MonsterSpawnInfo`)과 위치 스트림(`SnapshotNtf`)만 본다. 새로 필요한 것은 **게임데이터 테이블 2개(`SpawnGroup`/`Spawner`) + enum 1~2개 + Stage 당 `MonsterSpawner` 컴포넌트 1개 + NavMesh 랜덤포인트 함수 1개**다. 배치는 **하나의 스포너 개념을 두 모드(radius=0 고정앵커 / radius>0 밀도존)로** 표현해 하이브리드를 단순하게 만든다.

> **확정된 결정 (12장 요약):** ① 배치 = 하이브리드(스포너 단일 개념, radius로 앵커/존 구분), ② 무엇을 스폰 = `SpawnGroup`(팩 구성, 재사용), ③ 리스폰 단위 = **팩 단위**(팩 전멸 → 카운트다운 → 재배치), ④ 밀도 = `Spawner.MaxPacks` 동시 팩 수, ⑤ 활성화 = 플레이어 근접 게이팅(빈 존은 dormant — D4 스트리밍의 서버측 대체), ⑥ 스폰 위치 = NavMesh 랜덤포인트(존) / 고정좌표(앵커), ⑦ 틱 = `Stage::OnStageUpdate`(컨텐츠 스레드, 락 없음), ⑧ 신규 패킷 = 0.

## 1. 디아블로4 몬스터 스폰 분석

공개 자료(공식 강연 없음)와 인게임 동작에서 확인되는 D4 스폰의 골격. 핵심은 "**밀도(density)로 손맛을 만들고, 무리(pack) 단위로 배치하며, 빠르게 재생성해 월드가 늘 살아있게** 한다"는 점이다.

**(1) 밀도 그라디언트.** D4는 지역·콘텐츠마다 몬스터 밀도가 다르다(오픈월드 < 나이트메어 던전 < 헬타이드). 밀도가 곧 ARPG의 핵심 손맛이고, 블리자드는 출시 후에도 "엔드게임 몬스터/엘리트 밀도 증가"를 지속적으로 패치해 왔다.

**(2) 무리(pack) 배치.** 몬스터는 낱개가 아니라 **무리로** 깔린다. 엘리트는 "큰 엘리트 1 + 미니언 5"가 한 팩으로 나오고 팩이 affix를 공유한다. 챔피언은 3~5마리 팩으로 나온다. 잡몹도 군집으로 배치된다.

**(3) 빠른 리스폰 / 월드 재생성.** 오픈월드 몬스터는 **약 15~20초**면 다시 차오른다. 텔레포트하거나 던전을 다녀오면 직전에 죽인 몬스터가 전부 되살아난다. → "월드가 비지 않는다"는 체감.

**(4) 인스턴스 던전은 리스폰 없음.** 인스턴스 던전 내부에서는 리스폰이 없다. 대신 **나갔다 다시 들어오면 전체 리셋**(몬스터·보스·전리품 재생성)된다. 파밍 루프의 기반.

**(5) 스트리밍(주변 스폰/원거리 정리).** 플레이어 주변에 채워지고, 멀어진 곳은 정리된다(클라이언트 관점에서 시야 밖은 안 보임). 서버는 광활한 월드 전체를 항상 풀로 굴리지 않는다.

**(6) 특수 스폰.** 헬타이드/판데모니움 균열 같은 이벤트는 **밀도·엘리트 비율을 끌어올리고**, 희귀(rare) 몬스터는 정해진 지점/확률로 등장한다.

**가져올 것 / 버릴 것 (우리 게임 = 가벼운 hack&slash, 지속형 공유 월드 MMO)**

| D4 요소 | 우리 채택 | 비고 |
|---|---|---|
| 무리(pack) 단위 배치 | **채택 (핵심)** | `SpawnGroup`(팩 구성) + 런타임 `Pack`. v1의 주제 |
| 밀도 그라디언트 | **채택** | 존별 `MaxPacks` 동시 팩 수로 밀도 표현 |
| 빠른 리스폰(15~20s) | **채택** | 팩 전멸 → `RespawnDelayMs` 카운트다운 → 재배치 |
| 던전 리스폰 없음 + 재입장 리셋 | **채택** | 던전 = `RespawnDelayMs<0`(1회 스폰). 리셋은 기존 던전 인스턴스 생애주기로 자연 충족 |
| 스트리밍(주변 스폰/원거리 정리) | **변형 채택** | 서버는 **per-player 스트리밍 안 함**(공유 월드라 부적합). 대신 **존 활성화 게이팅**(플레이어 없는 존은 dormant) + 기존 AOI 가시성(클라 spawn/despawn). 2장 참조 |
| 엘리트/챔피언 affix 공유 팩 | 나중 | v1 팩은 구성·대형만. affix 공유는 엘리트 단계 |
| 월드이벤트/헬타이드 surge | 나중 | 스포너에 surge 모드 얹어 확장 |
| 난이도/파티원수 밀도 스케일링 | 나중 | `MaxPacks`/`SpawnGroup`에 배율만 얹으면 됨 |
| 팩 어그로 전파(한 마리 깨면 팩 전체) | 나중 | `몬스터AI.md` 와 동일하게 보류. 런타임 `Pack` 객체가 훅 제공 |

## 2. 핵심 설계 원칙

### 2.1 "스폰은 서버 내부 사건 — 클라는 가시성만 본다"

가장 중요한 결정. **클라이언트는 스포너/존/팩/리스폰타이머를 전혀 모른다.** 와이어를 건너는 것은 이미 있는 두 종류뿐이다:

1. **가시성** — 몬스터가 내 AOI에 들어오거나 나갈 때 `ObjectVisibilityNtf`(`MonsterSpawnInfo` / `despawn_ids`). 이미 `Stage::SpawnMonster`/`DespawnMonster` 가 호출한다.
2. **권위 트랜스폼** — 위치/회전/이동 (`SnapshotNtf`, 매 tick).

따라서 **스폰 시스템에 신규 패킷은 0개**다(`몬스터AI.md` 가 "신규 1개"였던 것보다도 적다). 스포너를 어떻게 재설계해도 — 고정앵커든 밀도존이든 surge든 — 클라 코드는 0 변경이다. 이것이 `몬스터AI.md` 2장 원칙("관측 가능한 행동만 복제")의 스폰 버전이다.

### 2.2 D4 "스트리밍"의 올바른 번역 — per-player 스트리밍이 아니라 존 활성화

D4(주로 소규모 파티 인스턴스/오픈월드)는 플레이어 주변에 몬스터를 채우고 멀어지면 정리한다. **우리는 다수 유저가 공유하는 지속형 Stage**라 "플레이어 주변에만 몬스터 생성"을 서버 객체 단위로 하면(per-player streaming) 같은 Stage의 유저 A와 B가 서로 다른 월드를 보게 되어 깨진다. 그래서:

- **몬스터는 Stage에 지속 존재**한다(공유 권위). **per-client 시야 처리는 이미 AOI**가 한다(sector 진입/이탈 시 spawn/despawn Ntf — `Stage.cpp` 의 visibility 로직).
- D4 스트리밍의 **CPU 절감 의도**는 **존 활성화 게이팅**으로 가져온다: 활성화 반경 안에 플레이어가 한 명도 없는 존은 **dormant**(리스폰·밀도유지 정지). 플레이어가 들어오면 깨어나 채운다. 이는 `몬스터AI.md` 6장의 거리/관여도 LOD(적응형 주기)와 같은 발상이다.

> 결과: "월드가 살아있다"는 체감(빠른 리스폰)은 유지하면서, 아무도 없는 광역 필드를 헛돌리지 않는다.

## 3. 개념 모델 — Spawner / SpawnGroup / Pack

세 개념으로 충분하다.

```
GameData_Spawner   (정적: 어디에·얼마나·언제)   ─┐
                                                  ├─► MonsterSpawner (Stage 당 1개, 런타임 관리자)
GameData_SpawnGroup(정적: 무엇을 — 팩 구성)     ─┘        │  소유
                                                          ▼
                                                   Pack (런타임: 한 번 깔린 무리 1개)
                                                          │  멤버 objectId 들
                                                          ▼
                                                   Monster × N  (기존 객체, Stage 소유)
```

| 개념 | 종류 | 책임 |
|---|---|---|
| **`GameData_Spawner`** | 게임데이터(정적) | **얼마나/언제** — SpawnGroup + 동시 팩 수(MaxPacks) + 리스폰 지연 + 활성화 모드. **위치/반경은 여기 없음** — 유니티 에디터 배치(`Stage스크립트.md` §5 레이아웃)에서 같은 Key로 온다 |
| **`GameData_SpawnGroup`** | 게임데이터(정적) | **무엇을** — 한 팩의 구성: (monsterKey, 수)들 + 대형/산개 반경. 여러 스포너가 재사용 |
| **`MonsterSpawner`** | 서버 런타임 컴포넌트 | Stage 당 1개. 자기 Stage의 스포너 행들을 소유, 매 tick 밀도 유지·리스폰·활성화 판정 |
| **`Pack`** | 서버 런타임 객체 | 한 번 배치된 무리 1개. 멤버 `objectId` 목록 보유, 전멸 감지 → 리스폰 트리거. (나중) 어그로 전파 단위 |

설계 노트: 스포너와 그룹을 **분리**하는 이유는 `몬스터AI.md`가 AI 프로파일을 분리한 것과 같다 — 같은 무리(예: "고블린 3마리")를 맵 곳곳의 여러 스포너가 재사용한다.

## 4. 하이브리드 배치 — 스포너 단일 개념, radius로 두 모드

기획자가 고른 "존 밀도 + 기획자 앵커 하이브리드"를 **별도 테이블 두 개로 만들지 않는다.** 하나의 `Spawner` 가 `Radius` 의미만으로 두 모드를 표현한다(시니어 엔지니어 기준 과설계 회피). **위치(center)와 반경(radius)은 유니티 에디터에 놓인 Spawner 오브젝트(`Stage스크립트.md` §5 레이아웃)에서 오고**, `GameData_Spawner`(같은 Key)는 동작 파라미터만 갖는다:

| 모드 | 조건(레이아웃 radius) | 동작 | D4 대응 | 용도 |
|---|---|---|---|---|
| **고정 앵커(FixedAnchor)** | `Radius == 0` | center 좌표에 **정확히** 팩 배치 | 희귀몹 지점, 던전 인카운터 | 네임드 위치, 관문 수호, 던전 방 |
| **밀도 존(DensityZone)** | `Radius > 0` | center 중심 반경 내 **NavMesh 랜덤포인트**에 절차적 배치 | 오픈월드 밀도 | 필드 군집, 사냥터 |

밀도(개수)는 `MaxPacks`(동시 존재 팩 수)로 표현한다. 앵커는 `MaxPacks=1`(반경0 + 팩1)인 밀도존의 특수 케이스로 자연스럽게 통합된다.
좌표를 에디터 레이아웃으로 일원화한 이유: 기획자가 csv에 좌표를 손입력하기 어렵고, 스크립트(`ActivateSpawner`)·레이아웃·스포너 동작데이터가 **같은 Spawner Key** 로 묶이기 때문이다.

### 4.1 NavMesh 랜덤 배치

밀도존 배치엔 NavMesh 위의 랜덤 walkable 좌표가 필요한데 **현재 없다**(`StageNavMesh` 는 `SamplePosition`(스냅)·`FindPath` 만 제공). 신규 함수 1개를 추가한다:

```cpp
// StageNavMesh: center 주변 radius 내 walkable 랜덤 좌표. dtNavMeshQuery::findRandomPointAroundCircle 래핑.
bool SampleRandomPoint(float cx, float cy, float cz, float radius,
                       float& outX, float& outY, float& outZ) const;
```

- **팩 대형:** 팩 리더 1마리를 `SampleRandomPoint(center, radius)` 로 배치 → 나머지 멤버는 리더 주변 `SpawnGroup.ScatterRadius` 만큼 오프셋한 좌표를 기존 `SamplePosition`(스냅·walkable 검증)으로 보정. 보정 실패(걸을 수 없는 곳)면 리더 위치로 폴백. (멤버 배치는 별도 랜덤 없이 `SpawnMonster` 의 스냅 경로를 그대로 탄다.)
- 고정앵커(radius=0)는 랜덤 없이 center 그대로 기존 `SpawnMonster` 경로(NavMesh 스냅 포함)로 배치.

> `SpawnMonster` 가 이미 NavMesh 스냅 + 월드경계 검증 + 거부 처리를 하므로, 스포너는 좌표만 계산해 넘기면 된다. 배치 안정성은 기존 경로가 보장한다.

## 5. 리스폰 / 밀도 유지 로직

### 5.1 팩 단위 리스폰 (확정 결정 ③)

리스폰을 **몬스터 1마리 단위가 아니라 팩 단위**로 한다(D4의 무리 체감과 일치, 관리 단순). 매 tick `MonsterSpawner::Update(deltaMs)` 가 자기 스포너들을 순회:

```
for each Spawner s (활성 상태):
    살아있는 팩 수 alive = count(s.packs where pack.IsAlive())
    # 1) 전멸한 팩 정리 + 리스폰 예약
    for each pack in s.packs:
        if pack.justCleared():            # 멤버 전원 디스폰됨
            if s.RespawnDelayMs >= 0:
                pack.respawnTimerMs = s.RespawnDelayMs   # 카운트다운 시작
            else:
                remove pack               # 던전: 리스폰 없음
    # 2) 카운트다운 만료 → 재배치
    for each pack with respawnTimerMs expired:
        replace pack in-place (NavMesh 랜덤 재배치)
    # 3) 밀도 미달이면 새 팩 (최초 채움 / 던전 외)
    while alive + pending < s.MaxPacks:
        spawn new pack
```

- **팩 전멸 감지 = 폴링.** 스포너가 매 tick 팩의 멤버 `objectId` 들을 `Stage::FindObject` 로 조회해 생존 수를 센다(팩 수가 적어 비용 무시). 몬스터에 역참조(packId)를 심는 침습적 콜백은 v1에 불필요 — `몬스터AI.md` 가 캐스트 타겟을 포인터 대신 `objectId` 로 보관한 것과 같은 결(despawn 안전).
- **시체와의 관계:** 사망 후에도 시체(corpse, 30초)가 유지되며 그동안 `m_monsterObjects` 에 남는다. 리스폰 카운트다운은 **시체 디스폰(객체 제거) 이후** 시작하는 게 자연스럽다 → 폴링이 `FindObject==nullptr`(=디스폰 완료)를 생존0으로 판정하면 자동으로 그렇게 된다. (즉 "시체 30초 + 리스폰 지연" 이 직렬로 더해진다. 합산 시간을 줄이려면 `RespawnDelayMs` 를 작게.)

### 5.2 활성화 게이팅 (확정 결정 ⑤)

각 스포너에 `ESpawnActivation`:

| 모드 | 동작 |
|---|---|
| `Always` | 항상 밀도 유지(보스 앵커, 던전 등 항상 채워둘 곳) |
| `PlayerProximity` | 활성화 반경 안에 플레이어가 1명 이상일 때만 밀도 유지/리스폰. 아무도 없으면 dormant(틱 스킵). 비활성 전이 시 기존 몬스터는 **그대로 둔다**(갑자기 사라지면 부자연) |
| `Manual` | 스크립트가 `ActivateSpawner(key)` 를 부르기 전까지 dormant. 켜진 뒤엔 `PlayerProximity`/`Always` 규칙을 따른다. 웨이브·이벤트 연동용(`Stage스크립트.md`) |

활성화 판정은 Stage의 sector/유저 목록을 이용(존 center 주변 sector에 유저가 있는지). AOI 순회 헬퍼(`ForEachUserInAoi`)와 동일한 격자 조회를 재사용.

### 5.3 필드 vs 던전

| | 필드(오픈월드, `Field`) | 던전(`PublicDungeon`/`UserDungeon`) |
|---|---|---|
| 스포너 모드 | 주로 DensityZone + `PlayerProximity` | 주로 FixedAnchor + `Always` |
| 리스폰 | 있음(`RespawnDelayMs>=0`) | **없음**(`RespawnDelayMs<0`) — 1회 스폰 |
| 리셋 | 월드 지속(리스폰으로 자연 재생성) | **인스턴스 재생성**으로 충족 — 던전을 나갔다 새로 만들면 새 Stage라 스포너가 다시 OnStart에서 채움. 별도 리셋 코드 불필요 |

> 던전 "재입장 리셋"은 우리 던전 생애주기(유저던전 1시간/닫기, 공용던전 시간창)가 **새 Stage 인스턴스**를 만들어 자동 충족된다 — D4 동작과 동일한 결과.

## 6. 게임데이터 설계

게임데이터 파이프라인 규칙(`게임데이터.md`): 숫자접미 순회(`MonsterKey1/2/3` → `GetMonsterKeyCount()/GetMonsterKey(i)`), enum 0=None 자동, 출력 대상 server/client/all.

### 6.1 신규: `GameData_SpawnGroup` (팩 구성 — 무엇을)

| 컬럼 | 타입 | 출력 | 설명 |
|---|---|---|---|
| `Key` | int32 | all | 스폰그룹 키 |
| `Name` | string | all | 라벨(예: GoblinTrio) — 참고용 |
| `MonsterKey1` | int32 | server | `GameData_Monster.Key`. **순서=대형 기준(첫번째=리더 자리)** |
| `MonsterCount1` | int32 | server | 그 몬스터 마릿수 |
| `MonsterKey2` | int32 | server | (없으면 0). 숫자접미 규칙으로 `GetMonsterKeyCount()/GetMonsterKey(i)` 자동 |
| `MonsterCount2` | int32 | server | |
| `MonsterKey3` | int32 | server | 필요 수만큼. v1 잡몹 팩은 1~3종이면 충분 |
| `MonsterCount3` | int32 | server | |
| `ScatterRadius` | float | server | 팩 멤버를 리더 주변에 흩뿌리는 반경(m) |

> 리더/미니언 affix 공유, 대형(진형) 세부는 **엘리트 단계(나중)**. v1은 "지정 마릿수를 ScatterRadius로 흩뿌려 함께 배치"까지.

### 6.2 신규: `GameData_Spawner` (배치 — 어디에/얼마나/언제)

| 컬럼 | 타입 | 출력 | 설명 |
|---|---|---|---|
| `Key` | int32 | server | 스포너 키. **에디터 레이아웃의 Spawner 오브젝트 Key 와 동일** (위치/반경은 거기서 옴) |
| `SpawnGroupKey` | int32 | server | `GameData_SpawnGroup.Key` 참조(무엇을) |
| `MaxPacks` | int32 | server | 동시 존재 팩 수(=밀도). 앵커는 보통 1 |
| `RespawnDelayMs` | int32 | server | 팩 전멸 후 재배치 지연. **<0 = 리스폰 없음(던전)** |
| `Activation` | enum `ESpawnActivation` | server | Always / PlayerProximity / Manual |
| `ActivationRange` | float | server | PlayerProximity 일 때 깨어나는 반경 |

> 전부 `server` 출력 — 클라는 스폰 데이터를 몰라야 한다(2장).
> **위치/반경 제거:** `CenterX/Y/Z`·`Radius`·`StageKey` 는 더 이상 csv에 없다. 위치·반경은 에디터 레이아웃의 Spawner 오브젝트(같은 Key)가 갖고, "어느 Stage 소속인지"도 그 Stage의 레이아웃 파일에 그 Key가 있느냐로 결정된다(`Stage스크립트.md` §5.3). 따라서 Stage는 OnStart 때 **자기 레이아웃이 가진 Spawner Key 들**에 대해 `GameData_Spawner::FindData(key)` 로 동작 파라미터만 끌어온다 — 테이블 전체 순회 불필요.

### 6.3 신규 enum (`GameEnum.xlsx` → `GameEnum_Monster` 또는 `GameEnum_Spawn`)

```
ESpawnActivation : None=0, Always=1, PlayerProximity=2, Manual=3
```

> (옵션) 모드 enum `ESpawnPlacement{FixedAnchor,DensityZone}` 를 따로 두지 않는다 — `Radius` 의미로 충분(4장). 기획자 가독성이 필요해지면 그때 추가.

### 6.4 기존 테이블 영향

- `GameData_Monster` : **변경 없음.** 이미 `Grade`(엘리트 단계 대비), `Exp`/`ItemDropGroup`/`IsItemDrop`(보상 — 별도 시스템) 보유.
- `GameData_Stage` : 스폰 자체를 위한 컬럼 추가는 없음. 단, 스크립트 연동을 위해 `ScriptName#` 컬럼이 추가된다(`Stage스크립트.md` §12). 스포너 목록은 Stage의 레이아웃 파일(에디터 export)에서 온다.
- **`Monster` 런타임:** 스폰 시 자신을 만든 `spawnerKey` 를 태깅(0=스포너 무관). 스크립트의 스포너별 사망 콜백(`OnSpawnerMonsterDead`, `Stage스크립트.md` §Q4)용. 태깅만 추가, 그 외 변경 없음.

## 8. 스레드 / 생애주기

- **틱 위치 = `Stage::OnStageUpdate(deltaMs)`** (확정 결정 ⑦). 이미 가상 훅이 있고(`Stage.h:292`, `Field`/`Town` 이 override) Stage가 **단일 컨텐츠 스레드**에서 처리되므로 **락이 필요 없다**(프로젝트 컨벤션). `MonsterSpawner::Update(deltaMs)` 를 여기서 호출.
- **ServerBase 타이머 스레드 금지.** 리스폰 타이머를 별도 타이머 스레드에 걸면 Stage 객체를 크로스스레드로 만지게 되어 위험하다. 리스폰 카운트다운은 `OnStageUpdate` 안에서 `deltaMs` 누적으로 처리한다(`몬스터AI.md` 의 캐스트 타이머가 매 tick integrate 되는 것과 동일).
- **멤버는 `objectId` 로 보관.** `Pack` 은 `shared_ptr<Monster>` 가 아니라 `int64 objectId` 목록만 갖는다. 생존 판정은 `Stage::FindObject(id)`. 몬스터 생애주기(Stage `m_monsterObjects` 소유 + 시체/디스폰)와 결합하지 않아 안전.
- **초기 채움:** `Stage::OnStart` 에서 **레이아웃의 Spawner 목록**(key+pos+radius)을 읽고 각 key 의 `GameData_Spawner` 동작 파라미터를 결합 → `Always`/이미 활성인 존 최초 채움. `Manual` 존은 스크립트가 켤 때까지 dormant.

| 위치 | 현재 | 바꿀 방향 |
|---|---|---|

| `Field::OnStageUpdate` (`Field.cpp:21`) | 비어있음("향후 몬스터 스포너" TODO) | `m_spawner.Update(deltaMs)` 호출 |

| `Stage::SpawnMonster` (`Stage.cpp:394`) | 단건, AI=FSM 고정, 좌표 인자 | **재사용**(시그니처 유지). 스포너가 좌표 계산해 호출. (AI 주입은 기존대로) |
| `Stage::DespawnMonster` (`Stage.cpp:472`) | 단건 제거 + despawn 통보 | **재사용**. 스포너는 폴링이라 직접 안 부름(시체 만료 경로가 호출) |
| `StageNavMesh` | `SamplePosition`/`FindPath` | **`SampleRandomPoint(center,radius,out)` 신규**(`findRandomPointAroundCircle` 래핑) + `Stage` 에 얇은 래퍼 |
| `Monster` | 스폰앵커/리쉬 보유 | 리쉬·스폰앵커 재사용. **`int32 m_spawnerKey` 태깅만 추가**(스포너별 사망 콜백용, 0=무관) |

**신규 클래스 `MonsterSpawner`** (Stage 소유, owner=`Stage*` 백포인터):
```cpp
class MonsterSpawner {
public:
    void Load(Stage& stage, const StageLayout& layout);  // 레이아웃 Spawner 목록 + 각 key 의 GameData_Spawner 결합
    void Update(int64 deltaMs);                           // 활성화 판정 + 전멸 폴링 + 리스폰 + 밀도 유지
    void Activate(int32 spawnerKey);                      // 스크립트 ActivateSpawner (Manual 존 깨우기)
    void Deactivate(int32 spawnerKey);
private:
    struct Pack { std::vector<int64> memberIds; int64 respawnTimerMs; bool pending; };
    // pos/radius 는 레이아웃에서, 동작 파라미터는 GameData_Spawner 에서.
    struct ActiveSpawner { const GameData_Spawner* data; Vector3 center; float radius; bool active; std::vector<Pack> packs; };
    void spawnPack(ActiveSpawner& s);                     // SpawnGroup 읽어 SampleRandomPoint/center 로 SpawnMonster ×N (멤버에 spawnerKey 태깅)
    bool isPlayerNear(const ActiveSpawner& s) const;
    Stage* m_pStage = nullptr;
    std::vector<ActiveSpawner> m_spawners;
};
```

| `spawnPack` — SpawnGroup 읽어 리더=`SampleRandomPoint`/앵커=center, 멤버=ScatterRadius 오프셋+스냅, `SpawnMonster ×N` | 팩이 한 무리로 흩뿌려져 배치, 앵커는 정확 위치 |
| `Update` — 활성화 판정 + 전멸 폴링(`FindObject`) + 리스폰 카운트다운 + `MaxPacks` 밀도 유지 | 팩 전멸→`RespawnDelayMs` 후 재배치, 동시 팩 수 ≤ MaxPacks, `RespawnDelayMs<0` 은 재배치 안 함 |
| `isPlayerNear`(ActivationRange) 게이팅 | 플레이어 없으면 dormant(리스폰 정지), 들어오면 재개 |

### P3 — Stage / Field / Town 배선

| 작업 | verify |
|---|---|
| `Stage` 에 `MonsterSpawner m_spawner`, `OnStart` 에서 `Load`+초기채움, update 경로에서 `Update(deltaMs)` | 마을/필드 시작 시 데이터대로 스폰 |
| `Town::OnStart` 하드코딩 스폰 제거 | 하드코딩 없이도 스포너로 동일/의도된 스폰 |
| `Field::OnStageUpdate` 가 `m_spawner.Update` 호출 | 필드 밀도 유지·리스폰 동작 |

### P4 — 통합 검증

| 시나리오 | verify |
|---|---|
| 필드 밀도존: 입장 시 MaxPacks까지 채움, 팩 잡으면 15초 후 재생성 | 화면 + 로그 |
| 고정앵커: 정확 좌표 1팩, 잡아도 리스폰 없음(또는 Always면 유지) | 화면 + 로그 |
| 활성화 게이팅: 멀어지면 리스폰 정지, 다가가면 재개 | 로그(dormant 전이) |
| 던전: 1회 스폰·리스폰 없음, 재입장(새 인스턴스) 시 다시 채움 | 화면 |
| 다수 팩 + 다수 유저: 폴링·밀도유지 부하/프레임 | 서버 CPU |
| 가시성: AOI 진입/이탈 시 기존 spawn/despawn Ntf 정상(신규 패킷 0) | `packet` 치트 |

**완료 정의(v1):** 필드·던전이 **데이터만으로** 무리 단위 몬스터를 깔고, 필드는 빠르게 리스폰해 월드가 비지 않으며, 던전은 1회 스폰 후 재입장 리셋되고, 빈 존은 dormant로 CPU를 아끼고, 클라엔 신규 패킷 없이 기존 가시성으로만 보인다. `Town`/`Field` 의 하드코딩 스폰이 남아있지 않다.

## 13. 구현 현황 (v1 — 실제 코드 / 데이터 / 보정)

> 이 장은 설계(1~12장) 위에 **실제로 구현·검증된 결과 + 구현 중 확정/보정된 사항**을 기록한다.
> 상태: **서버 구현 + 빌드 + 런타임 검증 완료.** 스폰·밀도·활성화·팩·리스폰 동작 확인(몬스터 생성 → 처치 → 리스폰).

### 13.1 구현된 것

- **게임데이터** (P0):
  - `SpawnGroup.xlsx` → `GameData_SpawnGroup` (`Key/Name/MonsterKey1~3/MonsterCount1~3/ScatterRadius`). 숫자접미 순회(`GetMonsterKeyCount/GetMonsterKey`, `GetMonsterCountCount/GetMonsterCount`) 생성됨.
  - `Spawner.xlsx` → `GameData_Spawner` (`Key/SpawnGroupKey/MaxPacks/RespawnDelayMs/Activation/ActivationRange`) — **좌표 컬럼 없음**(레이아웃에서).
  - `ESpawnActivation`(None/Always/PlayerProximity/Manual) enum.
- **NavMesh**: `StageNavMesh::SampleRandomPoint`(`findRandomPointAroundCircle` 래핑, 스레드별 RNG) + `Stage::SampleRandomNavPoint` 래퍼.
- **`StageLayout`**(신규): `Map/StageLayout/<stageDataKey>.json` 로드. v1은 `spawners`(key/pos/radius)만.
- **`MonsterSpawner`**(신규, Stage 소유, `friend`): `Load(layout)` + `Update(dt)`(활성화 판정·전멸 폴링·리스폰·`MaxPacks` 밀도) + `spawnPack`(리더=랜덤포인트/앵커=center, 멤버=ScatterRadius 산개) + `isPlayerNear`(sector) + `aliveCount`(FindObject 폴링) + `Activate/Deactivate`.
- **`Stage`**: `m_pLayout`(공유 불변 참조)/`m_pSpawner`(인스턴스별) 멤버, `OnStart` 셋업, `OnUpdate` 4.5단계 tick. `Town::OnStart` 하드코딩 스폰 제거.
- **레이아웃 공유**: `StageLayout` 은 인스턴스마다 파싱하지 않고 **`StageAssetManager` 가 시작 시 stageDataKey 별 1회 로드해 불변 공유**(`Stage스크립트.md` §18.5). `StageLayout` 은 `spawners` 외 `spawnPoints`/`waypoints` 도 로드.
- 신규 패킷 0(기존 가시성 재사용) — 설계대로.

### 13.2 설계 대비 보정된 사항

- **레이아웃 키 = `stageDataKey`** (`100.json`), navMeshFileName 아님 — 여러 Stage 가 같은 NavMesh 이름("Town")을 공유하기 때문(per-stage 분리). 설계 5.3/6.2 의 "NavMeshFileName 짝" 서술을 이 방식으로 대체.
- **`ESpawnActivation` 위치 = `GameEnum_Monster`** (신규 `GameEnum_Spawn` 안 만듦) — 프로젝트에 새 enum 파일 추가를 줄이기 위해.
- **리스폰 타이밍**: `aliveCount` 가 `FindObject` 로 생존을 폴링 → 시체(corpse 30초)가 디스폰된 뒤 리스폰 카운트다운 시작. 즉 "시체 + `RespawnDelayMs`" 직렬 합산(설계 5.1 노트대로).
- **`StageScript` 도 Stage 의 `friend`** (스크립트 스폰/스포너 API 가 `SpawnMonster`/`m_pSpawner` 접근). `MonsterSpawner` 와 동일 패턴.
- **`std::max` 매크로 충돌**(NOMINMAX 미정의) → 수동 비교로 회피(빌드 이슈 보정).
- 데이터 예시: `SpawnGroup` = SlimePack(51×3)/MixedCamp(51×2+50×1), 테스트 몹 key 50/51. 레이아웃 좌표는 운영 중 조정됨.

### 13.3 아직 안 된 것 / 다음

- **몬스터 `spawnerKey` 태깅 구현됨** — `Monster::m_spawnerKey`(게터/세터), `MonsterSpawner::fillPack` 가 스폰 시 그 스포너 Key 로 태깅(스크립트 직접 스폰=0). 이를 이용한 스포너별 사망 콜백(`OnSpawnerMonsterDead`, Q4b)이 `Stage스크립트.md` 쪽에 구현·런타임 검증됨(전역 `OnMonsterDead` 도 동일).
- **유니티 에디터 export 툴** 미구현 — 현재 레이아웃 json 은 손작성(부트스트랩).
- 엘리트/챔피언, 월드이벤트/surge, 난이도·파티 밀도 스케일링, 팩 어그로 전파, 드랍/보상 — 전부 "나중에"(10장) 그대로.
