# 폴더 구조
(서버 루트: %ROOT%\Server. GameServer 프로젝트는 상세히, 다른 서버/라이브러리는 이름·역할만 — GameServer 외 내부 구조는 확인 범위 밖이라 개요만.)

## 솔루션 프로젝트
- GameServer      : 게임 로직 서버 (Stage/Monster/Character/스킬/전투). ← 이 문서의 주 대상
- GatewayServer   : 클라 연결·라우팅(게이트웨이). 게임서버는 이 경유로 클라에 패킷 전송
- LoginServer     : 로그인/인증
- RegistryServer  : 서버 레지스트리
- CommunicationServer : 전체 채팅 fan-out, 귓속말 presence·라우팅. 상세는 `서버클라연동.md`의 "채팅 시스템" 참조
- ServerBase      : 서버 공통 베이스(컨텐츠 스레드, 패킷 직렬화, Prometheus 형식 `/metrics` endpoint 등). 각 서버가 사용
- NetLib          : IOCP 소켓·세션·송수신 (NetLib.md)
- PacketGenerator : .proto → C++/C# 패킷·데이터 구조체 생성 + 직렬화/디스패처 (PacketGenerator.md)
- GameDataLib     : 게임데이터(csv) 로드/조회. GameDataGenerator 생성 코드를 빌드 (게임데이터.md)
- GameDataGenerator : xlsx → csv + 코드(C++/C#) 생성기 (C#)
- DBConnector     : DB 접근 (`DB.md`), 현행 테이블 정의는 `DB스키마.md`
- Logger          : 로깅
- Recast / Detour : NavMesh 빌드·길찾기 라이브러리
- OUTPUT/         : 빌드 산출물 + 서버용 게임데이터(csv)/NavMesh(bin)

# 컨텐츠
- Stage 클래스
	- Stage는 캐릭터가 돌아다닐 수 있는 1개의 sector를 가집니다. sector는 grid 단위로 나누어져 있습니다.
	- 1개 Stage는 단일 스레드에서 처리됩니다.
	- Stage는 시스템 메시지큐를 가집니다. 이 메시지큐는 유저입장, 유저연결끊김, 서버종료 등의 시스템 메시지를 처리하기 위한 큐입니다.
	- Stage가 업데이트될 때 시스템 메시지큐의 메시지를 모두 처리합니다.
	- Stage는 자신 Stage에 속한 유저객체를 소유합니다.
	- Stage가 업데이트될 때 유저객체도 함께 업데이트합니다.
	
> 던전: 현재 **설계만 — 미구현.** `EStageType::Dungeon` enum 값은 있으나 Stage 파생 던전 클래스(공용/유저던전)는 아직 없다. 실제 구현된 Stage 파생은 Town/SystemStage/Field 뿐.

- 공용던전 클래스 (설계 — 미구현)
	- 공용던전은 Stage를 상속받습니다. 그래서 단일스레드에서 처리됩니다.
	- 게임서버가 생성하는 던전으로, 시작 시간과 종료 시간이 있습니다. 유저는 이 시간 사이에만 입장할 수 있습니다.
	
- 유저던전 클래스 (설계 — 미구현)
	- 유저던전은 Stage를 상속받습니다. 그래서 단일스레드에서 처리됩니다.
	- 1명의 유저가 생성한 던전입니다.
	- 던전을 생성한 유저가 유저던전을 닫거나, 1시간이 지나면 던전이 닫힙니다.
	
- 마을 클래스
	- 마을은 Stage를 상속받습니다. 그래서 단일스레드에서 처리됩니다.
	- 마을은 게임서버가 초기화될 때 생성됩니다. 이 때 **채널 수(ChannelCount)만큼 인스턴스가 생성**됩니다 (아래 "채널 시스템" 참조).
	
- SystemStage 클래스
	- SystemStage는 Stage를 상속받습니다. 그래서 단일스레드에서 처리됩니다.
	- 유저가 로그인에 성공하여 게임서버에 접속하면 클라이언트는 캐릭터 선택창으로 넘어가야 합니다. 그런데 유저 객체는 반드시 1개 Stage에 할당되어 있어야 하는데, 캐릭터 선택창은 마을이나 던전 등이 아닙니다. 그래서 캐릭터 선택창을 표현하는 SystemStage 객체를 만들어 유저를 여기에다 할당합니다.
	- SystemStage는 게임서버가 초기화될 때 생성됩니다. 채널 개념이 없어 **항상 1개**입니다 (StageManager가 유일하게 단수 캐시 `GetSystemStage()`를 유지하는 Stage).
	
- 컨텐츠 스레드
	- 컨텐츠 스레드는 ServerBase 라이브러리가 제공합니다.
	- 컨텐츠 스레드의 수는 `서버 CPU 코어 개수 - 1` 입니다.
	- 모든 Stage는 생성될 때 자신이 배정될 컨텐츠 스레드 번호를 다음 연산으로 찾습니다: `컨텐츠스레드번호 = 자신의ID mod 일반컨텐츠스레드수`
	
- 유저 클래스
	- 유저 1명을 나타냅니다.
	- 유저는 1개의 Stage 객체에 소유됩니다.
	- 유저는 Stage 객체가 업데이트될 때 업데이트 됩니다.
	- 유저객체에는 유저가 접속한 게이트웨이서버ID가 저장되어 있습니다. 유저에게 패킷을 보내려면 해당 게이트웨이 서버에 보냅니다.
	
- 유저의 Stage 이동 (동일 게임서버 / 다른 게임서버)
	- 처리 흐름·패킷·클라 규칙은 **서버클라연동.md 의 "스테이지 이동" 절** 참조.
	
- 게임서버가 게이트웨이 서버에 패킷전송을 요청할 때
	- 유저객체에 게이트웨이서버ID가 저장되어 있기 때문에 게임서버는 유저가 어떤 게이트웨이서버에 접속해있는지 알수있습니다. 이 게이트웨이서버에 패킷전송을 요청합니다.
	- 브로드캐스팅 할 때는 게임서버가 `게이트웨이서버ID : 유저ID목록` 으로 그룹화하여 유저가 접속한 게이트웨이 서버에만 유저ID목록을 전달합니다.

- 게임DB에 접근
	- 게임DB에서 유저데이터 읽는 시점
		- 유저가 게임서버에 입장할 때 게임DB에서 유저데이터를 읽어 유저객체를 생성합니다.
	- 게임DB에 유저데이터 업데이트 하는시점
		- 유저가 게임서버에서 나갈 때
		- 유저가 Stage를 이동할 때 
		- 던전 클리어 등의 중요 이벤트 발생 때
		- 마지막으로 업데이트한 지 3분이 지났을 때
	- DB 구성·접근 방식은 `DB.md`, 현행 테이블 정의는 `DB스키마.md` 참조

- DB 코루틴 (비동기 호출)
	- DB 접근은 DBConnector 의 AsyncDBQueue 로 비동기 처리한다. 핸들러를 코루틴으로 작성하고 `co_await m_dbQueue.ExecuteAsync(query, params, resumeExecutor)` 로 결과를 기다린다. (자세한 내용 DB.md)
	- DB 코루틴의 후속작업(resume)이 **어느 스레드에서 재개될지는 넘긴 `resumeExecutor`(db::IResumeExecutor)가 결정**한다.
		- 기본(IOCP): `GetCoroutineResumeExecutor()`. 게이트웨이 수신 경로에서 시작하는 코루틴(캐릭터 선택/생성/입장, 크로스서버 reroute 수신 등)이 사용. 후속작업이 Stage 를 직접 만지지 않고 스레드안전 경로(글로벌 유저맵 / 패킷송신 / EnqueueMessage)만 쓴다.
		- Stage 스레드: Stage 에서 시작하는 코루틴은 그 Stage 의 `GetResumeExecutor()`(= 배정된 컨텐츠 스레드)를 넘긴다. 그러면 후속작업이 같은 컨텐츠 스레드에서 재개되어, 인벤토리 갱신 같은 후속작업도 "Stage 는 단일 스레드에서만 처리" 불변식을 유지한다.
			- 구현: ContentsThread 가 태스크 큐를 가지고 매 tick drain 한다. 컨텐츠 스레드를 resume executor 로 노출하는 어댑터(ContentsThreadResumeExecutor)를 컴포넌트로 보유한다.
	- AsyncPin (수명 보호): Stage 에서 시작한 DB 코루틴은 prologue(첫 co_await 이전)에서 `pStage->PinForAsync(spChar)` 로 핀을 잡는다(RAII). 핀이 살아있는 동안:
		- 해당 Stage 는 파괴되지 않는다 (ContentsThread 가 제거를 미룸 — `Stage::IsBusy()`).
		- 해당 Character 는 Stage 에서 제거되지 않고(OnUserLeave 보류 → 핀 해제 후 처리), 다른 Stage 로 이동도 거부된다(handleStageMoveReq).
		- 핀 카운터(`Stage::m_inFlightAsync` / `Character::m_pendingAsync`)는 모두 Stage 스레드에서만 증감하므로 atomic/lock 불필요. 코루틴 프레임 종료(후속작업 완료) 시 자동 해제.

# 채널 시스템

## 개요
- **채널 = 같은 stageDataKey 를 갖는 Stage 인스턴스 N개.** 마을 4채널이면 같은 마을이 4벌 존재하고, 유저는 그중 한 곳에만 속한다.
- **클라이언트에 공개하지 않는다.** 유저는 채널을 선택할 수 없고 서버가 배정한다. 채널 번호는 로그/디버그용 식별자일 뿐이다.
- **게임서버 로컬 개념**이다. 서버 200의 마을 채널들과 서버 201의 마을 채널들은 서로를 알지 못하고, 번호가 일치할 필요도 없다.
- **Stage 단위로 독립**이다. 마을 채널과 필드 채널은 무관하며, 스테이지를 이동하면 목적지 채널을 새로 배정받는다.
- **정적**이다. 서버 시작 시 채널 수만큼 만들고, 런타임에 생성·파괴하지 않는다.
- 참고 모델: 디아블로4의 오픈월드 동적 샤드 / WoW 의 sharding (존 단위 분할, 유저에게 비공개).

## 채널의 필요성
- 마을·필드처럼 아무나 모일 수 있는 Stage 에 인원이 몰리면 브로드캐스팅 비용이 **O(N²)** 로 증가하기 때문에 인원을 분산시키려는 목적임.

## 게임데이터 (Stage.xlsx / Stage.csv — 서버 전용 컬럼)
| 컬럼 | 의미 |
| --- | --- |
| `ChannelCount` | 이 Stage 를 몇 개의 채널로 만들지. 서버 시작 시 이만큼 생성. 1 이상(0 이하면 서버가 기동하지 않음). |
| `ChannelSoftCap` | 채널당 목표 인원. 채널 선택 시 이 값 미만인 채널을 우선한다. **하드 상한이 아니다.** |

## 채널 선택 정책 — fill-first + 소프트캡
`StageManager::SelectChannel(stageDataKey)` 하나에 정책이 일원화되어 있다. **유저를 Stage 에 넣는 모든 경로는 이 함수를 거쳐야 한다.**

1. 유저수 < `ChannelSoftCap` 인 채널 중 **번호가 가장 작은 것**을 고른다.
2. 전 채널이 캡 이상이면 **유저수가 가장 적은 채널**로 폴백한다.

## 규약
- 채널 번호는 dataKey 별 **단조 증가**로 부여한다(재사용 없음). 

## 관련 파일
- `StageManager::SelectChannel` — 채널 선택 정책(유일한 진입점). 호출부: `Stage::executeLocalStageMove`(스테이지 이동), `GameServer::handleGatewayUserReroute`(크로스서버 도착), `GameServer::handleClientCharacterSelect`(캐릭터 선택 후 최초 마을 입장)
- `StageManager::registerStage` — 채널 번호 부여
- `GameServer::createStageChannels` — 부팅 시 ChannelCount 만큼 생성 (Town/Field 전용)
- `Stage::MoveToChannel` — 같은 stageDataKey 의 **지정 채널**로 이동. 치트 등에서 채널을 명시적으로 선택해서 이동할때 사용. 일반 입장 경로는 SelectChannel 을 쓸 것
- 데이터: `Stage.xlsx` 의 `ChannelCount` / `ChannelSoftCap`

## 치트
- `channel` — 현재 Stage 의 채널 현황(내 채널 + 채널별 인원) 보고
- `channel <no>` — 지정 채널로 강제 이동 (`Stage::MoveToChannel` 호출)

## 미구현
- **파티 어피니티 없음** — 파티 시스템이 추가될 경우(지금은 없음) 파티원들을 하나의 채널로 묶는 로직 필요. 친구 시스템이 추가될 경우(지금은 없음) 친구가 있는 채널로 이동하는 기능 추가 필요.

# 참고: 오브젝트 ID값과 게임데이터 Key값의 차이
- 게임내에서 오브젝트는 ID(int64 타입)로 구분됩니다. 게임 런타임에 생성됩니다. 게임전체에서 유일한 값입니다.
- 게임데이터는 Key(int32 타입)로 구분됩니다. 1개의 엑셀파일(예: Stage)에는 여러개의 Stage 데이터가 들어있습니다. 엑셀파일에 데이터마다 Key값이 미리 입력되어 있습니다. Key값은 1개 엑셀파일 내에서만 유일한 값이고, 다른 엑셀파일(예: Monster)에는 해당 파일만의 유일한 Key값이 또 있습니다. 그래서 서버에서 Stage 게임데이터를 얻으려면 GameDataTable_Stage::Find(key) 함수로 얻어야 합니다.



# 서버 tick
서버는 컨텐츠 스레드를 업데이트하여 서버 로직을 업데이트 합니다.  
1개 서버에 여러개의 컨텐츠 스레드가 있고, 1개의 컨텐츠 스레드는 여러개의 컨텐츠(Stage 등)를 소유합니다.  
1개 컨텐츠는 1개 컨텐츠 스레드에 소유되어 있어서 반드시 1개 스레드에서 처리됩니다.  
1개 컨텐츠는 여러개의 오브젝트(캐릭터, 몬스터, 프랍 등)를 소유합니다.  

서버의 tick은 50ms 입니다. 그래서 컨텐츠 스레드의 컨텐츠들(Stage 등)은 50ms 마다 업데이트 됩니다.  
하지만 컨텐츠 내의 오브젝트들의 업데이트 주기는 오브젝트의 종류마다 다릅니다. 오브젝트 종류별로 50ms의 배수(예: 100ms, 200ms)마다 업데이트될 수 있습니다.  
예를들면 유저, 캐릭터, 중요한몬스터(보스 등) 등의 중요한 오브젝트는 50ms 마다 업데이트 됩니다.  
일반 몬스터, 프랍 등의 중요하지 않은 오브젝트는 200ms 마다 업데이트 됩니다.  
컨텐츠 스레드는 50ms 마다 업데이트 되며, 50ms 마다 업데이트해야할 오브젝트 범위를 확인하여 업데이트 합니다.  
오브젝트는 생성된 다음 컨텐츠에 소유될 때 몇 ms 마다 업데이트 될지를 결정해야 합니다.  



# 스탯 컴포넌트

## 개요
- Actor(Character, Monster 등)의 모든 능력치를 관리. ActorObject 가 스탯 컴포넌트를 소유.

## EStat enum
- 개별 스탯. StrAdd, StrAddPct, StrAmp, StrReduce, StrTotal, HpAdd, HpAddPct, HpAmp, HpReduce, HpTotal 등
- StrTotal 같이 Total 이름이 붙은 스탯은 총합 스탯으로, 다른 스탯들을 모아 계산한 최종결과이다. 예를들면 StrTotal 은 StrAdd, StrAddPct, StrAmp, StrReduce 스탯들을 계산식을통해 합한 결과이다. Total 값은 대미지 계산등에서 빠르게 참조하기위해 사용된다. 각 스탯들의 계산식은 Stat 게임데이터의 StatOp컬럼(EStatOp 값)에 입력되어 있다.

## EStatGroup enum
- 스탯그룹. Str, Int, Hp 등. 개별 스탯은 1개의 스탯그룹에 속한다.
- 예를들면 StrAdd, StrAddPct, StrAmp, StrReduce, StrTotal 은 Str 그룹에 속한다.
- 개별스탯 <-> 스탯그룹 매핑정보는 Stat 게임데이터의 StatGroup 컬럼(EStatGroup 값)에 있다.

## EStatOp enum
- 스탯값을 Total에 계산해넣을 때 적용할 연산 종류 
- Add(합연산), AddPct(합연산%), Amp(곱연산), Reduce(점감곱연산), Total(총합) 이 있다.

## 스탯 컴포넌트 클래스
- StatComponentBase : 스탯 컴포넌트들의 부모클래스. EStatOp enum에 대한 스탯 계산식, Total 스탯 계산기능 등이 있다.
- BasicStatComponent : Character를 제외한 다른 Actor를 위한 스탯 컴포넌트. Total 스탯값들은 배열에 들어가있고, 나머지 스탯값들은 unordered_map에 들어가 있다.
- CharacterStatComponent : Character 만을 위한 스탯 컴포넌트. 모든 스탯값이 배열에 들어가 있어서 스탯을 매우 빠르게 조회할 수 있다.

## GameDataTable_Stat 클래스
- Stat 게임데이터 클래스. 모든 Stat 데이터는 여기를 통해 얻는다.

## Actor에 스탯 적용하기
- Actor가 초기화될 때(Initialize) Actor에게 적용될 수 있는 모든 스탯 데이터를 참조하여 Stat을 계산한다.
- 예) Character가 초기화될 때 JobBase 게임데이터에서 캐릭터 기본스탯 얻어서 적용, 캐릭터의 장비아이템에서 스탯값 얻어서 적용, 캐릭터의 마스터리 등에서 스탯값 얻어서 적용, 이후 게임플레이를 하면서 추가되는 스탯들(버프, 아이템장착 등)을 더하거나 빼면서 스탯을 유지시켜 나간다.
- 예) Monster가 초기화될 때 Monster 게임데이터에서 몬스터 기본스탯 얻어서 적용, 이후 게임플레이를 하면서 추가되는 스탯들(버프 등)을 더하거나 빼면서 스탯을 유지시켜 나간다.

## 참고사항
- 스탯값은 double 타입이기 때문에 더하거나 빼면서 부동소수점 오차가 누적될 수 있다. 하지만 이는 작은 값으로 간주하고 무시한다.
- 스탯의 소스(기본스탯, 아이템, 마스터리, 버프 등)는 따로 관리하지 않는다. 소스 자체가 게임내에서 참조가능하기 때문에 소스 자체에서 스탯을 얻을 수 있기 때문이다(소스를 따로 관리해야 되는 케이스가 있으면 그때 수정).
- 현재 HP, 현재 MP 값은 EStat 에 없다. 현재 체력 값은 ActorObject 클래스(Actor 들의 부모 클래스)가 별도 멤버로 가지고 있다.

## Total 스탯
- Total 스탯 계산 공식: Total = Add × (1 + AddPct×0.01) × (1 + Amp×0.01) × (1 − Reduce×0.01)  
- Total 스탯 말고 다른 스탯이 갱신될 때마다 해당 그룹의 Total을 즉시 재계산 한다.

## 대미지 계산
- 공격력, 스킬대미지 Total 스탯을 참조하여 게임로직 내에서 계산할 예정. 예: 공격력 = f(StrTotal, 무기...)). 아직 개발안됨.




# StageObject
StageObject는 Stage에 속할 수 있는 오브젝트이다.  
ActorObject, Monster, Character 등은 모두 StageObject를 상속받는다. (Monster/Character 는 ActorObject 경유.)  
EventArea(이벤트영역)는 ActorObject 가 아니라 StageObject 를 직접 상속받는다 — 위치/모양만 갖고 HP·스탯이 없으며 AOI 가시성 통보도 하지 않는다.  

## 객체 생성/초기화
- StageObject, ActorObject, Monster, Character 등 Stage 내 오브젝트는 파라미터 없는 생성자로 생성한 뒤 `bool Initialize(...)` 로 초기화한다.
- 상속 체인은 각 레벨의 Initialize 가 부모의 Initialize 를 명시적으로 호출한다 (Character::Initialize → ActorObject::Initialize → StageObject::Initialize).

# 몬스터
- Monster 클래스는 ActorObject 를 상속받는 게임 런타임 오브젝트이다. DB에 저장되지 않으며 Monster 게임데이터로부터 생성된다.
- Stage가 shared_ptr로 Monster를 관리한다. 
- 의사결정(AI)은 교체 가능한 컴포넌트 IMonsterAI(FSM/BT 등)가 담당하고, Monster 는 컴포넌트가 호출하는 공유 행동 API(이동/타겟/스킬/사거리)와 상태(위치/스탯/스킬/스폰지점)를 제공한다.
- 경량 스탯 컴포넌트(BasicStatComponent)를 사용한다.

# 전투 / 사망 처리
- 대미지 적용은 Stage::ApplyEffectDamage 로 일원화한다. 스킬 직격, 범위공격(AreaEffect), 지속피해(DoT 버프) 모두 이 경로를 거친다 (오브젝트에게 대미지를 주는 로직은 한 곳).
- 사망은 명시적 상태다(현재HP 0 파생이 아님). ActorObject 가 사망 플래그를 가지며, MarkDead(killerObjectId) 로 1회만 전환된다. 대미지가 아닌 사인(스크립트/지형 등)도 이 경로로 처리할 수 있다.
- 사망과 디스폰은 분리한다:
	1. HP 0 또는 명시적 사인 → MarkDead → 주변 AOI 유저에게 ObjectDeathNtf 브로드캐스트(클라가 사망 애니메이션 재생).
	2. 시체(corpse)는 일정 시간(현재 30초) 유지된다. 그동안 그 몬스터는 AI/이동 정지, 타게팅 대상에서 제외, 추가 대미지 차단.
	3. corpse 시간이 지나면 디스폰한다. 디스폰 통보는 별도 패킷이 아니라 ObjectVisibilityNtf 의 despawn_ids 를 재사용한다.
- 순회 중 컨테이너 변경 금지: 사망 만료된 몬스터는 updateMonsters 순회 중 제거하지 않고 모았다가 순회 종료 후 디스폰한다.
- corpse 유지 중 새로 AOI에 진입한 유저에게는 MonsterSpawnInfo.is_dead = true 로 내려, 클라가 사망 포즈로 표시한다.
- (스크립트 연동) 사망 경로에서 StageScript 의 `OnMonsterDead`/`OnSpawnerMonsterDead` 콜백 + `WaitForMonsterDead` 시퀀스 재개가 발동된다 — watch 등록된 monsterKey/spawnerKey 만 Lua 진입(대량몹 부하 방지). 자세한 내용 Stage스크립트.md.
- 리스폰 / 드랍 / 보상은 아직 미구현 (사망·디스폰 위에 얹을 예정).

## 시야(LoS) 검증 — 벽 너머 전투 차단
- **원리**: 벽/절벽은 NavMesh 표면이 끊긴 곳이므로, `dtNavMeshQuery::raycast` 로 from→to 를 쏴서 끝점 전에 막히면(t<1) 차단으로 본다. `StageNavMesh::IsLineOfSight(from,to)` → `Stage::HasLineOfSight(...)` 로 노출.
  - fail-open: NavMesh 미준비 / 시작점 off-mesh / 쿼리 실패 시 가시(true) — 판정을 못 할 때 스킬/공격이 엉뚱하게 전부 막히지 않게 한다(안티치트가 아니라 게임플레이 판정용).
  - ⚠ NavMesh raycast 는 **지표 2D** 판정이라 입체 지형(다리/2층)에는 부정확하다 — 평지형 맵 전용. 입체 지형 도입 시 별도 3D 지오메트리(vmaps식) 필요.
- **폭발/범위(AreaEffect)**: `Stage::QueryEnemiesInShape` 가 `requireLineOfSight`(기본 true) 로 center→대상 LoS 를 검사해 벽 너머 대상을 제외한다. shape 판정을 통과한 후보에만 raycast(비용 절감). AreaEffect(폭발·얼음지대·블레이즈·전격방출·DoT)와 서버 몬스터 투사체가 공통으로 이 관문을 거치므로 한 곳에서 커버된다.
- **몬스터 AI**: `MonsterFsmAI` 가 공격 진입(inAttackBand)·유지(needReposition) 판정에 몬스터→타겟 LoS 를 재사용한다. 벽 너머면 공격하지 않고 접근/재배치로 전환한다(길찾기가 벽을 돌아감). 거리 조건을 통과했을 때만 raycast 한다. (자세한 내용 몬스터AI.md)
- **미구현(보류)**: 플레이어 투사체 **직격**의 서버 LoS 검사(`OnSkillProjectileHit`, 시전위치→타겟)는 아직 없다. 클라 투사체가 이미 벽에서 소멸(클라이언트.md 물리 레이어 규약)해 정상 클라는 관통하지 못하므로, 모디파이드 클라 방어용이라 핵 검사 정책상 후순위. (진행 상황: Document/이동_투사체_개선계획.md)

# 상태 모니터링

GameServer는 공통 `/metrics` endpoint에 서버 전체 상태와 Stage별 상태를 Prometheus 형식으로 노출한다.

- 전체 상태는 scrape 직전에 thread-safe map과 Stage의 atomic user hint만 조회한다: `mmo_game_users`, `mmo_game_gateway_connections`, `mmo_game_communication_connections`, `mmo_game_stages{stage_type}`, `mmo_game_stage_user_hint_total`.
- Stage의 일반 container는 exporter thread가 읽지 않는다. 각 Stage가 자신의 ContentsThread에서 5초마다 snapshot을 만들어 atomic gauge에 게시한다.
- Stage label은 cardinality가 제한된 `stage_data_key`, `stage_type`, `channel`만 사용한다. runtime `stageId`, user/object/projectile ID는 label로 사용하지 않는다.
- Stage snapshot에는 user와 타입별 object, pending message/leave, in-flight async, event area, AreaEffect, projectile group과 실제 projectile, actor cast/buff, monster skill, sector 총수/점유/max가 포함된다.
- `mmo_game_users`와 `mmo_game_stage_user_hint_total`의 차이는 입장/이동 중이거나 Stage 반영을 기다리는 user를 찾는 교차 검증 값으로 사용한다.

세부 metric 목록, 수집 주기와 운영 도구 구성은 `Document/서버모니터링.md`를 따른다.
